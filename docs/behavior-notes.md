# Behavior notes

Developer notes: traps, invariants and external-system quirks, grouped by module.

## core / Blocks

- `TaskList`: the "feito" key is the exact line (without newline) plus its occurrence index, so two identical lines stay distinct. The occurrence is counted over every line, the same way `deleting` counts. When the removed line was the last one and had no newline, the line before it keeps its own newline. Splitting is on "\n" only (Foundation literal search, not `split`): Swift reads "\r\n" as one Character that never equals "\n", and rejoining with "\n" must give the same bytes.
- `CommandTemplate`: each value is passed as one single-quoted shell word (`it's` -> `'it'\''s'`), so a key with spaces or quotes cannot split or inject.
- `BlockCommand`: runs through `zsh -c` with the login shell's PATH (a GUI app inherits a minimal one); blocking, call off main. The shell leads its own process group so a timeout signals it and everything it started (SIGTERM, then SIGKILL shortly after; always reaped). The parent closes its copies of the child's pipe ends, or the readers never see EOF. Both pipes are drained while the process runs, so a large output cannot stall it; after exit it waits at most a second for readers (a background child may hold the pipe).
- `AlertList`: `nivel` is `red` or `yellow` (anything else reads as yellow); open time is `aberto_ts`, else `ts`; red first, then newest. Dates accept ISO 8601 with or without fractional seconds and `Z` or `-03:00` / `+0530` offsets.
- `AgendaList`: `allDay` events carry dates, not times; a `declined` response is excluded from now / next / count; all-day first, then by start.

## core / Agenda (native Calendar and Reminders)

- `AgendaService` runs over the `AgendaStore` protocol (`EventKitStore` in production, a fake in tests); `wisp-agenda` is only its `main`. Output is JSON on stdout; an error is one pt-BR line on stderr: exit 1 generic, 2 permission, 3 needs the user's confirmation (event with guests).
- Permission: denied, restricted and write-only read as "no access" (the message says "ler" for reads and "alterar" for create/edit/delete/complete; write-only says Wisp only has write access and needs full access) and are never asked again (the error names Ajustes do Sistema > Privacidade e Segurança); only `notDetermined` asks (the one system prompt), waiting at most 60 s: past that it exits 2 with "abra o Wisp no Mac e permita a agenda em Ajustes > Agenda". `calendarios` still lists the kind that was granted. `permissao` prints `{"eventos": state, "lembretes": state}` without asking; `permissao --pedir` asks for the undetermined ones. Ajustes > Agenda ("Agenda: permitir acesso") runs the embedded helper this way from the app process, so the prompt is attributed to Wisp; a helper started by the Telegram bot (launchd) may need that grant done once from the app first. Both Info.plists carry the usage strings and both signatures carry `com.apple.security.personal-information.calendars` (the helper target also sets `CODE_SIGN_ENTITLEMENTS`, so Debug and local builds have it). Not verified on a real prompt.
- Recurring events: `eventos` prints `"recorrente": true` and an occurrence id `<eventIdentifier>@<start ISO>`; the store finds that occurrence by searching one day around the start and matching the identifier and the start to the second, then uses `.thisEvent`. Edit or delete of a recurring event by its bare id is refused; `--serie` is explicit and uses `.futureEvents` (that occurrence and the next ones, "esta e as próximas"; never the past ones, so not the whole series). A bare id that ends in `@something` that is not a date-time (Google ids) stays whole.
- Edit and delete of an event with guests need `--confirmo` (exit 3 otherwise); it is a convention the agent must only pass after the user said yes, not enforcement. Edit also checks the final end against the final start (all-day events may be equal).
- Limits: `eventos` ranges are clamped to 92 days and cut at 200 items, and the output is `{"events": [...], "truncado": bool}`; `lembretes` without `--pendentes` returns pending ones plus those completed in the last 30 days (completed with no date are left out).
- Ranges: `--hoje` is today 00:00 to tomorrow 00:00 (local zone); `--semana` and the default are the next 7 days from today 00:00; a date-only `--ate` includes that whole day; no `--ate` means 7 days after `--de`. Output times are ISO 8601 with the local offset; an all-day event prints dates (`yyyy-MM-dd`) with an inclusive end, as EventKit stores it.
- Input times accept ISO with offset (`-03:00` or `-0300`), `yyyy-MM-ddTHH:mm[:ss]` or `yyyy-MM-dd HH:mm` (local zone) and `yyyy-MM-dd` (date only). An event whose start and end are both date-only is all-day; a reminder with a date-only `--quando` has a due date without time.
- Calendar and list names match case- and accent-insensitively; an unknown or ambiguous name errors with the options, a read-only calendar refuses writes.
- Event ids are EventKit's `eventIdentifier`: a recurring event keeps one id for the whole series, and edit and delete use `.thisEvent`, so they touch the occurrence EventKit resolves for that id. Reminder ids are `calendarItemIdentifier`.
- `wisp agenda` (Python) forwards its arguments untouched to the helper: `$WISP_AGENDA_BIN`, else `/Applications/Wisp.app/Contents/Helpers/wisp-agenda`, else `~/Applications/Wisp.app/...`. The runtime lives in `~/.local/share/wisp/runtime`, outside the app, so the app is found by those paths; the app sets `WISP_AGENDA_BIN` from `Bundle.main` in the agent's environment, so any install location works for it; if `WISP_AGENDA_BIN` is set but the file is missing, the command errors instead of trying the other paths. A helper killed by a signal returns exit 1 with a pt-BR line, never a negative code.

## core / Settings

- `HexColor`: `#RRGGBB` only; the 3-digit shorthand is rejected, not expanded.
- `WispSettings`: a custom theme picks accent, background and surface; the rest is derived. If the default text does not reach WCAG AA contrast (4.5) over a custom background, the side with better luminance is used. Saved tile order is always a permutation of `DashboardTileID.defaultOrder` (unknown ids and repeats dropped, missing appended). Files written before `dashboardOrder` existed decode to the default order. An unknown preset id (or "custom" without colors) falls back to the default lime.
- `WispSettings.settingsSection`: the Ajustes tab last opened; nil or an unknown id opens the first one (Aparência).
- `SettingsStore`, `ConversationStore`, `ClipboardStore`: written atomically; a corrupt file is moved to `<name>.bad` (a second corruption overwrites the older `.bad`) and defaults are used; the move is reported through the store's recovery note.

## app / Settings

- `IntegrationsPane`: one dropdown row per integration, one open at a time, all closed on arrival. `expandOnOpen` is a main-actor static set right before navigating to Ajustes > Integrações (the Música tab's "Abrir Ajustes") and cleared the first time the pane appears.
- `SpotifySettingsCard(embedded: true)`: inside an Integrações dropdown it has no title and no card of its own, since the host row already says "Spotify".
- `ToggleRow`: the whole row flips the switch (the switch itself ignores hits); an `accessory` before the switch keeps its own clicks.

## core / Memory, Routines, Profile

- `MemorySearch`: the search template fills `{query}` / `{root}` with shell-quoted values and must print `path<NUL>line:text` (grep/rg `--null -n`) or `path:line:text` (the first `:<digits>:` ends the path). BSD grep does not descend into a symlinked root (for example a vault linked into iCloud Drive), so commands get the symlink-resolved path. Obsidian names a vault after its folder; the `obsidian://open` URL percent-encodes every reserved character in both values, `/` included. Title matches sort first, else command order.
- `Routines`: `launchctl print` exits 113 ("Could not find service") for a label that is not loaded. Only the job's own top-level keys (one tab deep) are read; nested blocks such as the resource coalition repeat `state = active` and are ignored. Log tails read at most `maxBytes` from the end and drop a partial first line; "\r\n" is one Character in Swift, so it is a separator of its own.
- `Profile`: a `blocks` value of an unknown shape is ignored instead of failing the whole profile; a block with no command is a hidden tab.

## core / Spotify

- `SpotifyAuth`: PKCE verifier is 48 random bytes, base64url without padding (64 characters; RFC 7636 allows 43-128). The redirect is the loopback IP literal `127.0.0.1`: Spotify rejects `localhost` and allows plain HTTP only for loopback literals. A refresh response may omit `refresh_token`; then the previous one stays valid.
- `SpotifyModels`, `SpotifyRequests`: Feb 2026 API changes: a playlist's `tracks` became `items` (`tracks` kept as a deprecated fallback) and a playlist row's `track` became `item`; dev-mode `GET /search` allows at most 10 per type. An element that is `null` or undecodable decodes to nil so one bad item never drops a page. Episodes carry their own images instead of an album. Player 404 = no active device; player 403 with `PREMIUM_REQUIRED` (or a "premium" message) = not a Premium account. The play target is the active device, else this computer, else any controllable one.

## core / Memory graph

- `LinkGraph`: links resolve like Obsidian: by basename, case-insensitive, shortest path first; an unresolved link becomes a ghost node, except attachment extensions (never ghosts). Edges are undirected and de-duplicated, stored with `a < b`. Code fences and inline code are ignored when extracting links. The scan caches link targets by mtime and size; iCloud files not downloaded (`SF_DATALESS` flag, or legacy `.name.md.icloud`) are never read, since reading would block on a download. The base path goes through `realpath` so it matches the `/private/var/...` form the enumerator yields.
- `GraphLayout`: d3-force model with Barnes-Hut repulsion. Cooling is 300 steps from alpha 1; when most positions come from the cache it starts lower and settles in about 100. Seeding indexes each source once (O(N)); the layout on screen wins over the one on disk. Nodes without a seed start beside a seeded neighbour, else on a phyllotaxis spiral. A drag holds alpha at 0.3 (d3 `alphaTarget`); link strength is d3's `1 / min(degree)` times a multiplier; collision is one d3 forceCollide iteration, unscaled by alpha, on a grid of cells two max-radii wide. Panel values out of range clamp, missing ones default.

## core / Agent, Store, Telegram

- `AgentSession`: decoding under the lock keeps yields in stream order across handler invocations. Orphaned grandchildren can hold the pipes open, so the exit is emitted once the process is gone anyway.
- `ClaudeLocator`: the login-shell PATH is computed once per process.
- `ConversationReducer`: pure state machine over session events; when the session is gone, no queued turn can still produce a result.
- Permission prompts (confirmed against Claude Code 2.1.327 in a scratch folder, 18/11/2026): in `-p --input-format stream-json` a tool call that needs approval reaches the host only with `--permission-prompt-tool stdio`. Without it (`--permission-prompts` defaults to `host`, an `initialize` control request sent or not) the call is denied on the spot (`system/permission_denied`, `permission_decision.source: "config"`). No `initialize` is needed. The CLI writes `{"type":"control_request","request_id":R,"request":{"subtype":"can_use_tool","tool_name","display_name","input","description","permission_suggestions":[...],"blocked_path"?,"tool_use_id"}}` right after the assistant's `tool_use` and holds the call until the host writes one line on stdin: allow `{"type":"control_response","response":{"subtype":"success","request_id":R,"response":{"behavior":"allow","updatedInput":{...}}}}` (`updatedInput` may be left out in this version; Wisp echoes the input), "always" adds `"updatedPermissions":[suggestions]`, deny `{"behavior":"deny","message":M}`. Deny makes M the tool result (`is_error`, source `user_reject`) and Claude goes on; the tool still lands in the result's `permission_denials`, so the reducer drops the "libere em settings.json" hint for tools the user denied. Suggestions seen: `addRules` (`destination: "localSettings"`, i.e. `<cwd>/.claude/settings.local.json`; Bash `touch probe1 *`, WebFetch `domain:example.com`), `addDirectories` and `setMode acceptEdits` (both `session`). Sending all of them also switched the session to `acceptEdits` (a `system/status` line), so "Sempre permitir" sends only `addRules` with a non-session destination and shows only when there is one (Write offers none). `control_cancel_request` (drops a queued request) is handled but was not observed. Other `control_request` subtypes are ignored: Wisp registers no hooks or SDK MCP servers.
- Permission modes: `--permission-mode` accepts `default` (the help lists `manual`; init reports `default` for it), `auto`, `bypassPermissions`; the flag beats `permissions.defaultMode` in settings, and with no flag the CLI uses that setting. `auto` ran in `-p` on the owner's account (init `permissionMode: "auto"`, calls accepted with `reason_type: "mode"` or `"classifier"`; the classifier even accepted `rm -rf` of a sibling scratch folder). If the CLI reports another mode at init after Wisp asked for `auto`, the conversation says so and Ajustes shows Automático disabled for the rest of the run (how an account without `auto` behaves was not observed). `bypassPermissions` still runs `PreToolUse` hooks (a scratch hook exiting 2 blocked the call, `source: "hook"`) and `permissions.deny` rules (`reason_type: "rule"`), so the harness deny list and the secrets guard hold in every mode.
- Explicit `ask` rules in bypass (measured 20/11/2026, Claude Code 2.1.329): `claude -p --model haiku --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --permission-mode bypassPermissions --settings '{"permissions":{"ask":["Bash(*aprender add*)"]}}'`, asked to run `./fakewisp aprender add "regra teste"`: init reported `permissionMode: bypassPermissions`, the CLI emitted a `control_request` `can_use_tool` for that Bash command, and the command did not run while the request stayed unanswered. So an `ask` rule with a leading `*` matches and prompts even in bypass. Without a prompt host (`-p` without `--permission-prompt-tool stdio`, as in the Telegram bot today) such a call is refused.
- `PermissionSetting`: Wisp's own setting (only set while the profile is a link) wins, then the profile's `agent.permissionMode`, then `permissions.defaultMode` from `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR`), shown as "Definido no Claude" and never written. Unknown values count as unset. The profile is rewritten with sorted keys; a missing profile gets the persona/agent defaults the app needs to decode it.
- `TranscriptReader`: incremental, a line is read only once its newline lands. The project folder name is the cwd with every character outside `[A-Za-z0-9]` replaced by "-", one per Unicode scalar (same as the bot's `sessao.slug`). The CLI writes one line per content block. Injected prompts (slash commands, local command output, reminders), interrupt placeholders and the bot's own follow-up turn are not part of the conversation; when the session moved machine the bot wraps the user's message in context and the message follows a marker.
- `TranscriptFollower`: state is touched on its queue only. A missing file is a real state (a topic before its first turn): reported once, empty. On change the next poll reopens whatever sits at the path; a replaced file is read again from the start with a fresh parser. The descriptor outlives the dispatch source, never the reverse.
- `TelegramHTML`: `&amp;` is unescaped last so `&amp;lt;` becomes `&lt;`, not `<`. It also reads `br`, `blockquote` (`> `) and `strong`/`em`; Markdown code the model wrote (a fence or an inline span) is left as typed, so a `<b>` shown as code stays a literal. It runs once, when text enters the app: `ConversationReducer` (live `text` and `result`) and `TranscriptParser` (history, follower, previews), never again at render.
- `AgentInstructions`: the prompt (`--append-system-prompt`, `ClaudeCommand`) and env the app gives its `claude`. An app turn ALWAYS gets `appFiles` ("here" is the app: a file is a `[name](file:///abs/path)` Markdown link that opens on click; tested against `cli/tests/fixtures/contract/app-files-instruction.txt`), whatever else the conversation is. In a topic with a known wisp binary (`TelegramBlock.binary`, the unquoted `<bin>` of the `list` template; nil for a custom one) it appends `appSharedNote` (files linked here are sent to the topic automatically; only on an explicit ask for Telegram/the phone, `"$WISP_BIN" topic enviar --thread="$WISP_TOPIC_THREAD" FILE`) and sets `WISP_BIN` and `WISP_TOPIC_THREAD`. The bot's own turns get `telegramFiles` (= `TELEGRAM_FILES`, tested against `telegram-files-instruction.txt`): enviar to the topic. Both texts forbid calling the Telegram API directly and reading the bot token. After an app turn on a shared conversation, `FileLinks.absolutePaths` collects the `file://` links of the final assistant text (existing, readable, regular files, at most 10 and 50 MB each, outside the bot's deny-list folders, deduplicated) and the mirror passes them, plus the user's attachments, as `arquivos` of `telegram.post`, so the phone gets the file too. `TurnRestartPolicy` restarts a warm process whose topic differs from the conversation's current one (`contextChanged`), so a conversation unshared from Telegram stops carrying the bot's env.
- `TelegramTopics`: one conversation = one Claude session; Mac only. The bot runs a topic's turns and the app runs the app's, each under the flock of `~/.local/state/wisp/locks/<session_id>.lock`, so two turns of one session never overlap. A section's conversation is the one whose id equals the topic's `conversation` (or, for a topic without one, whose `sessionId` equals the topic's `sessionId`); the app shows "Respondendo pelo Telegram…" while the lock is held elsewhere. Wisp reads the transcript and talks through the profile's `blocks.telegram` commands: `status`, `list`, `share`, `post`, `close` and optional `attachments`. A partial `blocks.telegram` counts as no Telegram. `topics == nil` (never read) keeps every conversation in Wisp. `reading` comes from the status `reader` and is always this Mac.
- `ClaudeCommand`: `--permission-prompt-tool stdio` sends every prompt to the host as a `can_use_tool` control request; without it a prompt in `-p` mode is denied on the spot. A variadic flag goes before another flag so that flag ends its list.
- `FileOpenPolicy`: a click on a `file://` link opens only known document types in the default app; everything that could run or install (programs, scripts, archives, installers, launchers, bundles, shortcuts, macro files, executables on disk, unknown types) is revealed in Finder instead. The decision uses the symlink-resolved path.
- `FileLinks` / `SentFiles`: the files a reply hands over are the `topic enviar` calls the agent made plus the reply's `file://` links, deduplicated by resolved path (a symlink, `..` or `~` spelling of one file is one file) and capped at `FileLinks.maxFiles`. The shell expands `~/` and `$HOME/` before `wisp` sees the path, so the parser mirrors that. Anything the bot would refuse (its denied folders, unreadable or over-limit files) is skipped; APFS ignores case, so `~/.SSH` is `~/.ssh` and the comparison is case-insensitive and by file identity where the path exists.
- `PhoneHandoff`: the message the topic gets on "Continuar no celular" quotes the last reply the user can read (the one before the streaming one while a turn runs), cut at a word with an unclosed code fence closed. A pending approval can only be answered on the Mac: the bot cannot reach the process that holds it.
- `RuntimeLifecycle`: idle runtimes with a live process beyond the `keepWarm` most recent, or unused for `idleTimeout`, lose their process (state stays, the next message resumes); the conversation on screen and any busy runtime are never returned, and busy ones do not count toward the cap. A runtime with nothing left to keep is dropped and rebuilt from the transcript. In the sidebar an approval waiting or an unseen reply (attention) outranks a running turn.
- `ConversationTitle`: the title is the first message cut at a word boundary until one `claude -p` call (cheapest model, no session file, no tool, hook, skill or MCP server) writes a real one; a failure or timeout keeps the cut, and a conversation reopened from a record never asks for one.

## core / Usage, System, Media, Clipboard, Shell

- `UsageAggregator`: only files modified inside the window are opened, streamed line by line; each `message.id` counts once; a cheap byte check skips lines without usage. Cache reads are reported apart from the turn's spend. `UsageIndex` keeps the parsed lines of each transcript between reads (a week is hundreds of MB; reading it all cost about 2 CPU-seconds each time Home opened). Transcripts are append-only JSONL: a file that grew is read from the byte just past the last newline read; one that shrank, is new, or kept its size with a different modification date is read whole (a rewrite to a longer file is indistinguishable from an append and is not detected). A last line with no newline yet is counted but read again next time. One lock guards the index; its only caller is the detached task of `UsageModel`.
- `PlanLimits`: Wisp never reads the OAuth token nor calls the usage API; limits come from the statusline's `rate-limits.json` or the CLI's `rate_limit_event`, newest wins. A window whose reset time passed is stale.
- `UsageFormat`, `SystemFormat`: a value that rounds up to 1000 carries into the next unit ("999,96 GB" -> next unit, not "1000 GB"). Disk and network use decimal units (Finder), memory binary (Activity Monitor).
- `CPUUsage`, `NetworkRate`: counters are 32-bit and wrap; deltas are taken modulo 2^32. Nil when the CPU count changed or no time elapsed.
- `TemperatureSummary`: `PMU* tdie*` are SoC die sensors (Apple does not say which die is CPU or GPU), `NAND*` the SSD, `gas gauge battery` the battery; implausible values (`tdev` sensors report about -22 C idle) are dropped.
- `ProcessTable`: `ps` is setuid and sees every user's processes, `proc_pidinfo` only ours; `%cpu` may be above 100 and may use a comma decimal; `comm` may contain spaces.
- `VolumeUsage`: `available` is `volumeAvailableCapacityForImportantUsage` (Finder, purgeable counted as free); `availableRaw` is `volumeAvailableCapacity`.
- `MemoryBreakdown`: App = anonymous minus purgeable; Used = App + Wired + Compressed; Cached = file-backed + purgeable. Pressure level values are the kernel's: 1 normal, 2 warning, 4 critical.
- `NowPlayingParser`: fields are joined by U+001F; AppleScript writes reals with the locale's decimal separator ("12,5" in pt-BR).
- `ClipboardHistory`: items carrying an nspasteboard.org concealed / transient marker (including older markers some apps still write) are never stored; copying the same content again moves the entry up keeping its pin; pinned items are never evicted; big text copies are not recorded.
- `NotchGeometry`: the band hugging the notch never changes between rest and active; active only adds a strip below it.

## core / Setup

- `CommandRunner` replaces the whole environment when one is given: for uv always pass `RuntimeBootstrap.processEnvironment(layout, base:)`, never `uvEnvironment` alone (PATH, HOME, proxies and SSL_* would be lost).
- Known gap: the runtime root is under `$HOME`; a home folder with a space is passed as separate argv/env values, but uv and the venv shebangs under such a path have not been run end to end.
- `SetupState` is read and written only through `SetupState.load/save` (ISO 8601 dates), so the wizard and the gate agree.
- Runtime sync (`RuntimeSync.run`) never has a total time cap: uv is killed (its process group) only after 3 minutes with no output and no growth of the cache, venv, python or tmp folders (`tmp` is the runtime's own `TMPDIR` for uv, so a silent sdist build still counts as progress), so a slow download is never cut off. `UV_LOCK_TIMEOUT` makes uv give up a held lock on its own; a lock failure is recognised only by uv's own wait messages, never by a generic error. A lock wait or a stall is retried once, and a failure ends with "Último passo: ..." naming the last step reached.

## app

- `NowPlayingService`: every script is wrapped in `is running`, so a player that quit between the check and the script is never relaunched by `tell`. `AEDeterminePermissionToAutomateTarget` blocks (with `ask` it waits on the system prompt): it runs on its own queue, never main, and a prompting request has its own queue so an unanswered prompt does not hold back the other player's checks. No query at launch, so the Automation prompt never appears out of context; only a player that already granted Automation is queried; the prompt comes from "Permitir controle". A grant is cached (the 1 s ticker must not hit tccd); a revoke surfaces as -1743. The wildcard permission check does not prompt, a real harmless Apple Event does. Local files and ads have no artwork URL; that must not hide the track.
- `ShellController`: window-server routing ignores `hitTest`, so outside the pill the window stops taking events outright; the global monitor keeps firing and flips it back when the cursor enters. Hover-open never steals the keyboard. Leaving `.panel`, a window that stays key keeps eating keystrokes, so it is cycled out of the window list and focus returns to the previous app only if the user did not switch apps meanwhile. Frames jump (not slide) across displays. `CGRect.contains` excludes the max edges; the cursor can sit exactly on the top edge.
- `WispAvatar`: the still figure (Reduzir movimento, or `animates` false) and the animated one draw the same parts; only the motion lives in Core Animation, so the render server runs it and the app does no per-frame work (the 30 fps `TimelineView` it replaced re-laid out the whole panel every frame). Layers are fixed; a size, accent or backing-scale change redraws their baked images and restarts the animations. Layer geometry is y-up. Animations run at 10-30 fps (30 fps is plenty for a 1.5 pt float). Blinks: three slots of 5.5 s per loop, each blink at a pseudo-random spot, so gaps vary from 4 to 7 s; the eyes close to 12 % for 0.16 s.
- `-WispOpenPanel <tab>` (a `PanelTab` raw value, e.g. `myMac`) opens the panel on that tab and keeps it open through outside clicks, to measure each tab without a mouse; `-WispNoKeychain` skips every Spotify keychain read and write (Spotify shows as not connected), so a freshly signed measurement build does not raise the keychain prompt on every launch. Both exist only in Debug and in builds compiled with `WISP_PERF`.
- `SpotifyKeychain.adoptLegacyItem`: copies the session saved under the previous bundle id's service, once, when the new service has none; the old item stays where it is.
- `PillView`: an always-on 30 fps timeline in the resting pill cost 6-12% CPU, so it animates only while busy. The pill sits in a top-aligned centered overlay so its fixed size never feeds back into the hosting view's window size.
- `ComposerView`: corner radius is half the one-line height; `.continuous` at that radius left a half-filled 1pt column at the leading edge. The AppKit layout callback is deferred because it may run inside a SwiftUI update.
- `SettingsView`: the color panel must float above the notch panel or it opens hidden behind it.
- `SidebarView`: the Cmd-N shortcut button uses `.opacity(0)`; `.hidden()` would drop the shortcut.
- `AppSettings`: writes go through one queue (ordered); a color picker drag is debounced; flush on terminate so a change inside the window is not lost.
- `TelegramModel`: a failed list read keeps the last list (a missing topic would hand its session to local `claude`); a topic closed from Wisp is hidden at once, since its note may say active until the next brain sync. There is no claim step: sharing a conversation runs `share` (a topic on the same session, with a recap), and after each app turn on a shared conversation the app runs `telegram.post` so the topic mirrors the user's message and the reply (`wisp topic postar`, no Claude run).
- `TabModels`, `DashboardModels`, `MemoryModel`, `RoutinesModel`, `TelegramModel`: live for the process (the panel view is rebuilt on every open) and never act as source: every read goes back to the profile's file or command, the newest read wins, and a forced read during a running one runs again after it (the running read may predate an action). The agenda command hits the network, so non-forced refreshes within `maxAge` keep the last result.
- `MessageRow` (assistant text): links open only for `http(s)` and `file://` absolute local paths; a clicked file opens in its default app, a `.app` or executable is revealed in Finder instead of run, a missing file does nothing.
- `ConversationViewModel`: every turn, from the app or the bot, runs under the flock of the session (`SessionLock`); a conversation linked to a topic is still the app's to run. The app takes the lock per turn and keeps a lease while turns are queued, released when the last result lands (or the session is discarded). Before a turn the warm `claude` process is restarted for a fresh `--resume` (so what the bot said is in the context) when the session is shared in Telegram, the lock was contended, or its file changed after the app's last turn; never while a turn is in flight (`TurnRestartPolicy`), and the restart keeps pending turns, mirror users and the lease (`ConversationReducer.processRestarted`). Opening or starting a conversation resets the last-turn stamp. Session starts are serialized (one start at a time, the next waits for the stop) so two children never share one transcript; a start in flight notices a new generation and stops its own child. The pill reacts only to a result or phase change; `result` is the sole path that shows a reply in the pill.

Write/Edit/MultiEdit/NotebookEdit on a file inside a Wisp source checkout (a folder holding `bot/src/wisp_bot` and `cli/src/wisp`) only has its path checked. Limits: a script that builds a path or URL from pieces, a relative path reached after `cd` into a parent, or a file written elsewhere is not seen.

[ ] { }` in the arguments. `ask` for every other command that names `agenda`/`wisp-agenda`/`WISP_AGENDA_BIN` as a word (every create/edit/delete/complete, `./wisp`, `/tmp/x/wisp`, `mywisp`, `/tmp/wisp-agenda`, a bare `wisp agenda`, chained or computed commands, a bare `agenda`), and for a command that references `wisp`/`WISP_BIN`/`WISP_AGENDA_BIN` followed by a word with `$`, quotes, glob, braces or a backslash, or together with `eval` (`wisp ag""enda`, `a=ag; wisp ${a}enda`, `$WISP_BIN a* apagar-evento`); nothing for the rest (`topic enviar` keeps its normal flow). `permissions.ask` rules in `harness/settings.json` and in the app's and bot's guard settings (`guard-settings.json` fixture) cover the mutating subcommands in the forms the agent is told to use (`"$WISP_BIN" agenda X`, `$WISP_BIN agenda X`, `wisp agenda X`, `"$WISP_AGENDA_BIN" X`); per the Claude Code docs an `ask` rule prompts even in `bypassPermissions`, while a hook `ask` under bypass is not documented, so the rules are the part that holds there. `harness_merge` appends missing `ask` rules like `allow`/`deny`. Limit: this is best-effort defense in depth for the documented invocations. A copied helper binary, a variable holding the path (`c=$WISP_BIN; $c agenda ...`) or a script that calls the helper indirectly is not caught. A hook that cannot read its input exits 2 (the turn is refused).
- Guard hooks (`wisp hook guard-*`, `guard_destructive`): best-effort, not a sandbox. Every message starts with `GUARD_PREFIX`, the only thing the app treats as a guard block; a hook whose command cannot start would let the call through, so the turn does not start. The destructive guard casefolds every path comparison (the volume may be case-insensitive), expands `a{b,c}d` textually (comma lists only, nested, capped), reads the script of `sh -c`/`bash -lc` after the first short-flag cluster holding `c`, and remembers a lone `NAME=value` for a later `$NAME`; paths computed at run time or variables set outside the command are not seen.
- `session_lock` (bot): the blocking acquire runs in a thread; when the awaiting task is cancelled the thread still finishes, so a done-callback gives the lock back if it was won. The wait notice is cosmetic and never blocks the turn.
- Bot `_sh_err` (hosting): the child starts in its own session and a timeout kills its whole process group, like `sessao`/`topicos`.
- Send deny-list: `bot.py` (`NEGADOS_NOMES`, `NEGADOS_GLOBS`, `NEGADOS_PASTAS`) and `FileLinks.swift` (`denyNames`, `denyGlobs`, `denyDirs`) each hardcode the same lists; `cli/tests/fixtures/contract/send-denylist.json` is a drift test that fails if they differ, so change the three together. Besides names and folders, both sides read the first 4096 bytes of a file and refuse it if they contain `PRIVATE KEY-----` (or if the read fails); the marker and limit are in the fixture too. `.key` is not a denied name, so Keynote decks (zips) are sent.
- `hosting` pair rules (`hosting.py`): Telegram accepts ONE `getUpdates` per token, so two readers trade 409. Each bot is `active` (reads) or `standby` (only watches the other host). The claim `{host, ts}` lives only on the PC (`CLAIM`, survives reboot); nothing in the Wisp writes it any more, the PC loop rewrites it (`trocar_claim`, only over the claim it read) and copies it into its own `STATE` every beat, the Mac reads it on its normal check. PC with claim "pc" (or none) starts in `grace` for up to `GRACE_S`, then reads; the Mac seeing the grace stops reading and writes `peer-yielded` on the PC, which activates at once; Mac off or asleep = the PC waits the whole grace. PC with claim "mac" stays standby; if it was reading it yields only with no turn running and after pushing the notes, then stops the updater, lets the already-read updates become handlers and checks again (work arrived = reconnect and keep reading). Each Mac check writes `MAC_VISTO` on the PC (mtime = PC clock): no check for `MAC_FRESCO_S` (counted from PC boot) means the Mac slept, the claim returns to the PC and it reads without grace; Mac checking but not reading for `MAC_ESPERA_S` returns the claim through the grace; Mac in the post-409 block: the PC never yields to it, and if it already did the claim returns at once. `CLAIM_PENDENTE` (Mac only) holds a Mac claim that did not reach the PC; the loop delivers it on the first check that reaches the PC, dated from when it was asked, never over a newer PC claim; nothing in the Wisp creates that file today. The Mac reads at once on claim "mac"; otherwise only when the PC is not active/grace for `MISSES` checks in a row, or on the first check if Tailscale says the PC node is offline. An unreadable PC state (ssh/parse failed) never activates the Mac; only a valid "no bot" reading counts as a miss. Exception: ssh to Linux failing with "Host is down" / "No route to host" (kernel ARP unanswered) plus Windows ssh also mute, with the Mac on the PC's /24, is a valid "PC off" reading; timeout, refusal and auth stay unreadable. A 409 on the Mac drops the reading and blocks reactivation. All traffic goes through ssh Mac->PC: the tailnet ACL blocks the direct port (measured 30/09) and the Mac has no sshd; the PC never needs to reach the Mac. The PC clock stamps its own state (read with the PC's `date +%s`), so a skewed clock does not count. `solo` has one host: `rodar` activates the reading and only publishes the beat, no ssh.
- `hosting` vigia and probes: the Mac keeps a long ssh to the PC that prints one state line per second and, when the connection drops, its stdout closes and the next `echo` dies of SIGPIPE, so no orphan loop is left on the PC; a missing file is the line `{}`. A vigia "off" only wakes the Mac loop, which then does a real reading newer than it; only two mute probes after the PC closed the session skip that reading. The vigia never takes the Mac loop down. While releasing, the Mac never publishes standby until its running turn ends (the PC would read a forked session). The push has its own ceiling (process group killed); the outer timeout is only a safety net, and the handover never holds the yield.
- `sessao` (Mac <-> PC): the jsonl lives in `~/.claude/projects/<slug>/<session_id>.jsonl` with the slug being the absolute cwd with every non-alphanumeric replaced by "-"; copying it to the slug of the cwd where it resumes is enough for `claude --resume <id>` to recover the whole context, even when the `cwd` fields inside point to a path that does not exist here (verified 14/10). The Mac always starts (the PC cannot reach it) and the copy goes only over ssh: a session may hold secrets, so never through git or the brain. The remote shell on Windows is cmd.exe, which eats binary, so the file travels as base64 in a stream (never whole in memory; 57-byte multiples give 76-char lines with no padding in the middle) and integrity is checked by sha256. The PC does not pull, it asks: it leaves `<state_dir>/sessao-pedidos/<id>.json` and the Mac bot, which looks at the PC every hosting tick (30 s idle; 20 s missed the window), pushes the jsonl. A copy written in the last 2 minutes may have a live claude in it, so it is never replaced or deleted. The topic note decides the session: the host that takes over resumes the SAME one. A Mac turn in flight at the yield is marked on the PC (entries older than the expiry are junk from a Mac that died mid-turn; 60 s of clock slack); mirror candidates come from the PC's own `topics.json`, not the notes (which arrive up to 5 min late).
- `wisp arquivos` / `wisp mac` (`arquivos.py`, `mac.py`): every outside call (`mdfind`, `osascript`, `screencapture`, `pmset`, `open`, `/usr/bin/trash`) goes through the injected `Runner`, so tests never touch the Mac; osascript gets user text only after `--`, never inside the script. `buscar` reuses the send deny-list from `wisp_bot.bot` (`_negados`, `_fica_em_negado`), so there is still one list (and its fixture); it also drops `~/Library` and any hidden path component, and falls back to a bounded name walk (depth 6, 50000 entries) when `mdfind` fails or yields nothing usable. `organizar` looks only at the top level of a folder inside the home (never the home itself, `~/Library`, or a folder holding a project marker such as `.git`, `package.json`, `*.xcodeproj`), skips hidden files, symlinks and deny-listed files, and refuses a group folder that is a symlink, a regular file or resolves outside the organized folder (a warning in the plan, a failure at apply time). Names are free at plan time and again at apply time (`nome 2.ext`); the move itself is `renamex_np(RENAME_EXCL)` on macOS (link+unlink elsewhere), so it can never replace a file, and a dangling symlink counts as occupied. The journal `desfazer-<ts>.json` is one JSON object per line (header `{"version": 2, "pasta"}`, then `{"criada"}` / `{"de","para"}` lines), created before the first move and appended with fsync after each, so a crash or a failed move leaves a journal that undoes exactly what moved; a run that moves nothing leaves none, and two runs in the same second get `-2`. `desfazer` reads the whole journal first (a damaged one is refused without touching anything), restores in reverse with the same no-overwrite move, lists the files it could not restore, removes the folders the run created if empty and renames the journal to `desfeito-<ts>.json`. Trash moves are not in the journal (the Trash is the undo). `mac abrir` ports `FileOpenPolicy` by extension (no UTType in Python): folders, executables, files without extension, the app's reveal list and every extension not on the short safe-to-open list get `open -R` and the reply says it only showed the file; `open -a` is used only for an `.app` found by name in `/Applications`, `/System/Applications` (and their `Utilities`) or `~/Applications`. `mac print` writes to `~/.local/state/wisp/capturas/` (files older than a day are deleted on each print), not the Desktop; `--janela` waits for the user to click a window (`screencapture -w`, 60 s), so the instruction forbids it from Telegram. `mac nao-perturbe` only reads `~/Library/DoNotDisturb/DB/Assertions.json`, which macOS lets only an app with Full Disk Access read; without it the command says so (checked on macOS 27: "Operation not permitted"), and it never toggles Focus (private APIs). Permission denials are recognised from osascript's "not authorized" / -1743 text; a denied Screen Recording shows up as no output file. The app resolves `WISP_BIN` with `EngineGuards.wispBinary` (Telegram block, else the runtime or `~/.local/bin/wisp`), so the agent gets it without Telegram.

## Mac control (`wisp mac`, `wisp mcp mac`, `wisp-mac` helper)

- One tool set, three doors: `cli/src/wisp/mac_control.py` holds every action once (`TOOLS`); `wisp mac <cmd>` (CLI), the `wisp-mac` MCP server (`mac_server.py`, registered for Claude Code by `wisp setup harness` and for Codex by the managed block in `config.toml` and the `-c mcp_servers.wisp-mac.*` overrides) and the local engine (built-ins in `local/tools.py`, no MCP) all call `mac_control.call`, which is the only place that logs. A name or contract change goes in `TOOLS` and nowhere else. The three `mcp_overrides` (Python CLI, bot, Swift `CodexCommand`) must stay equal to `cli/tests/fixtures/contract/codex-mcp-overrides.json`; the instruction text (`AgentInstructions.macTools`, the bot's `MAC_TOOLS`) must equal `mac-instruction.txt`.
- Helper (`app/MacControl/main.swift`, logic in `core/Sources/WispCore/MacControl/`): AX API for the tree, press, menus and focus; CGEvent for typing (Unicode strings in chunks of 16 UTF-16 units; `\n` is the Return key, `\t` the Tab key), keys, point clicks and scroll. It lives in `Wisp.app/Contents/Helpers/wisp-mac`. No environment variable chooses it (the agent controls its own environment): `Ctx.helper()` looks only in the `.app` that contains the running Python (if any), `/Applications/Wisp.app` and `~/Applications/Wisp.app`, and runs it only after `codesign --verify --strict -R=<requirement>` passes, where the requirement is the Wisp.app's own Team ID (`anchor apple generic and certificate leaf[subject.OU] = "<team>"`) or, for a self-signed Wisp.app, its leaf certificate hash; an ad-hoc or unsigned app, or a helper signed otherwise, is refused (`Ctx.verify`, once per binary and mtime). `Ctx(test_helper=...)` is the only way to point elsewhere and nothing in the CLI or the MCP server sets it. `WISP_MAC_BIN` was removed from the app's turn environment and from the Codex `env_vars`. The helper also refuses every command except `permissao` and `selftest` unless the nonce on its stdin (an inherited descriptor, never the environment or argv) names a file the server wrote. `Ctx` generates a nonce per process (the MCP server, or one `wisp mac` run), creates `~/.local/state/wisp/mac-callers/<nonce>` holding the server's pid (folder 0700, file 0600, removed at exit and on SIGTERM, files older than 7 days swept) and writes the nonce plus a newline to the stdin of each helper child; the helper (`MacCaller.valid`) reads at most one line with a 2 s timeout and accepts only a 32-to-128 hex-digit nonce whose file exists, is a regular file (not a symlink), belongs to the same uid has no group or other permission bits, and holds the pid of a live process whose executable path contains `/wisp/runtime/` or `/Wisp.app/Contents/` (so a development run from a repo checkout is refused). This is a real comparison, not only a format check, but it is not a security boundary: any process of the same user can create such a file and pipe its name, and the agent's shell can do it unless `Write`/`Edit` deny rules (set on that folder) and the guard-outbound rule stop the obvious ways. A remaining same-user bypass is documented rather than closed: a shell can list the folder, read a nonce and a pid, and pipe that nonce to the helper's stdin while the real server is alive. It stops casual direct use and accidental calls. The real guard against a UI send is the approval card, enforced by the default-deny rule below and by the ticket. Exit codes: 3 no Accessibility permission (one sentence naming Ajustes > Controle do Mac), 4 watchdog (25 s, and every AX call has a 2 s messaging timeout, so an unresponsive app cannot hang a call), 5 a blocked send button, 6 a refused password field. `wisp-mac selftest` checks the parsers only: it touches no UI and asks for no permission. `permissao` reads `AXIsProcessTrusted` without a prompt; only `permissao --pedir` shows the system dialog.
- The tree prints `[n] Role/Subrole "title" desc="..." value="..." @x,y WxH`, indented by depth; `[n]` is the traversal order, capped at 400 elements and depth 8 by default (1500 and 20 at most). The value of a secure text field is never read (`value=<oculto>`). A click by title prefers an exact (case and accent insensitive) match over a partial one, and `--indice` picks among the matches; an AX press that fails falls back to a CGEvent click at the element's centre. Menu paths are walked through the AX menu bar and only the last item is pressed.
- Send rule, default-deny (`mac_control.needs_card`, `mac_send`). Outside the safe apps `tecla` is default-deny: only arrows, Tab, Esc, Delete/Backspace, Page Up/Down, Home/End (any modifiers) and exactly cmd+one letter or digit pass; everything else (Return, Enter, Space, F-keys, cmd+shift+letter, and any ctrl+letter, because ctrl+m, ctrl+j and ctrl+o act as Return) needs `mac_send acao=tecla`. In every app, including the safe ones, Space, Return or Enter on a focused pressable element whose title matches the send pattern is refused. Typing text with a newline, or clicking an element whose title, description, help or identifier matches the send pattern (`\b(send|enviar|envia|mandar|senden|envoyer|submit|post|publicar|responder|reply)\b` plus 发送, 送信, Отправить, Invia, Wyślij, Verstuur, Répondre, Skicka; camelCase and snake_case identifiers such as `SendButton` and `send_button` are split into words before matching, in Python and in the helper) is refused in every app except a short list where Return does not send: Finder, Preview, System Settings, Music, Spotify, Calculator, Calendar, Notes, TextEdit, Pages, Numbers, Keynote (compared as the whole app name, not a substring). The safe list and the never-safe list match by bundle id, which `foco` now returns (`bundle`); the display name is only for showing, so a Terminal renamed "Finder" is still a Terminal, and an app whose bundle cannot be read always needs the card. The defaults are `com.apple.finder`, `com.apple.Preview`, `com.apple.systempreferences`, `com.apple.Music`, `com.spotify.client`, `com.apple.calculator`, `com.apple.iCal`, `com.apple.Notes`, `com.apple.TextEdit` and `com.apple.iWork.Pages|Numbers|Keynote`; the `macSafeApps` setting now holds bundle ids. Terminal, iTerm, Xcode and every other app whose purpose is running commands or code are not on it: with one focused, typing a line plus Return runs a shell command, and Cmd+R in Xcode runs code. `NEVER_SAFE_BUNDLES` and `NEVER_SAFE_PREFIXES` (com.apple.Terminal, com.googlecode.iterm2, dev.warp.Warp-Stable, com.mitchellh.ghostty, net.kovidgoyal.kitty, org.alacritty, com.github.wez.wezterm, com.microsoft.VSCode, the Cursor bundle, dev.zed.Zed, `com.jetbrains.*`, com.apple.dt.Xcode, com.apple.ScriptEditor2, com.apple.Automator, com.apple.shortcuts, plus the automation tools com.raycast.macos, org.hammerspoon.Hammerspoon, `com.stairways.keyboardmaestro.*`, com.docker.docker, dev.commandline.waveterm and a few editors) can never be added, browsers and messaging apps neither, even if a user setting lists them. The list lives in the app's UserDefaults (`defaults export ai.wisp.app -`, key `macSafeApps`, an array of names the user can extend with `defaults write ai.wisp.app macSafeApps -array "Notion"`), read through the Runner; it is not a file under `~/.config`. Because `~/Library/Preferences/ai.wisp.app.plist` is a plain file, the agent is denied `Write`/`Edit` on it, on `~/Library/Application Support/Wisp/**` and on `~/.config/wisp/**`, and `Bash(*defaults*ai.wisp.app*)` (any path to `defaults`, `-currentHost`, write, delete or import), `Bash(*Preferences/ai.wisp.app*)`, `Bash(*ai.wisp.app.plist*)`, `plutil` and `PlistBuddy` on that domain, plus `Write`/`Edit` on `~/.local/state/wisp/mac-callers/**`, in `harness/settings.json`, `EngineGuards.settings` and the bot's `guard_settings` (contract `guard-settings.json`). The way through is `mac_send`, which always asks: `acao=tecla` (to=[key], subject=`tecla`, body=key), `texto` (to=[app], subject=`texto`, body=text), `clique` (to=[label], subject=`clique`, body=label) act in the target app after the allow, only if it is still the app named and the focus is a readable, non-secure field; `acao=script` (app=`AppleScript`|`JXA`) and `acao=atalho` (app=`Atalhos`) are below. With no `acao`, `mac_send` sends the message in the compose window of a messenger app or of a browser tab on webmail/chat (`sensitive(foco)`: the messenger list, or a browser whose `AXDocument`/title matches mail.google.com, outlook.live.com, outlook.office(365).com, office.com, web.whatsapp.com, messenger.com, web.telegram.org, discord.com, app.slack.com, teams.microsoft.com, teams.live.com or the words Gmail, WhatsApp, Outlook, Messenger, Telegram, Discord, Slack, Teams). The card is built from the window, not from the tree and not from focus: `wisp-mac composicao` returns, as the body, the AXValue of the largest editable (AXEditable, or a settable AXValue) AXTextArea or AXWebArea of the window (whole, no truncation, quotes untouched; if none qualifies the call refuses; it also refuses when the walk reaches the 1500-element cap, since the tree may be cut before the fields; every field comes from the same window walk), and To/Para, Cc, Bcc/Cco and Subject/Assunto from their labelled elements (own value, descendants, or the next text field), whatever has focus; for a chat app with no To field the conversation title stands in. Any Bcc refuses (`mac_send` does not send with a hidden copy), and the requested cc must equal the window's Cc exactly. `mac_open` refuses a `mailto:` that carries `cc`, `bcc`, `body`, `to`, `from`, `reply-to`, `in-reply-to` or attachment parameters or `&` before the `?` (`mailto:ana@x.com` and `?subject=` open), because it would prepare a message with recipients or text the user never sees. The requested `body`, `to` and `subject` must equal those values byte for byte after `canon` (NFC, CRLF to LF, trimmed), not a substring; a mismatch refuses and the error carries what the window holds so the model can copy it. After the allow, `wisp-mac enviar-janela --regex <send pattern> --esperado <json of body, recipients, cc, subject>` runs in one helper process: it reads the compose window again, refuses on any difference or any Bcc, finds the single AXButton in that window whose label matches the pattern (zero or several refuse), and presses it through `pressElement`, which walks the window once more and checks role, title and description at that index before pressing. There is no separate click process after the last read. The ticket hash is over the tool name, the `app`, to, cc, subject and body, in Python (`wisp_bot.broker.huella`) and in Swift (`BrokerCore.fingerprint(tool:_:)`, `authorize(inputJSON:toolName:)`), pinned by `ticket` and `ticket_mac` in `approval-broker.json`; a ticket for one tool or app is not accepted for another. Clicks always carry `--bloquear <send pattern>`, safe apps included (Calendar invites, iWork "Send a copy", Notes sharing); only outside the safe apps does the helper also run in strict mode (`--estrito`): any click on an AXButton, AXMenuItem, AXMenuButton or AXDefaultButton, or on any element that exposes the AXPress action (`pressable`) and is not a navigation role, asks for the card, whatever its label, and for a point click the same rule applies to the element and up to 3 ancestors (an image inside a button asks); text fields, links, tabs, disclosure triangles, scroll bars, static text and the like do not, and neither does a button with a label inside an AXToolbar (toolbar navigation; an unlabelled toolbar button does ask). Every menu action outside the safe apps asks (`acao=menu`: the real item is first resolved with `menu --exato --resolver`, its title must equal the typed last component, then the card, then the press); inside the safe apps `menu` always passes `--bloquear`, and the helper resolves the item first (a partial label such as `Message > Sen` resolves to `Send`), applies the pattern to the item's real title, and re-resolves and compares the title right before pressing. A point click is judged by the app that owns the element under the point (its AX pid); the helper checks the element and up to 3 ancestors (title, description, help, identifier); `pressElement` walks the window again right before pressing and refuses unless role, title and description still match and the pattern still does not match.
- Scripts (`mac_script`, or `mac_send acao=script`): no pattern decides that a script is safe, every script asks. Before the card, and without one if it hits: the script text and every `do shell script "..."` / `doShellScript('...')` body go through the secrets guard (`hook_guard_secrets`, `scan_text`, and a keychain/ssh pattern: `security find|dump|export|add|delete|import-*`, `find-generic-password`, `Library/Keychains`, `.keychain`, `~/.ssh`) and a hit is refused outright; they also go through `guard-destructive` and `guard-outbound` (mail sends; the UI-script rule is skipped here because the card is the control). The gate request carries the script as the body (the ticket hash is over those bytes) and an `exibir` copy with every control and format character (category C, except newline and tab) written as `\u{XXXX}`. Under Claude Code the model calls `mac_send` with `acao=script`, because only `mac_send` has the ask rule and ticket; `mac_script` itself works where the card is live (Codex, local engine) and fails closed under Claude. The script text is never logged (length only).
- Shortcuts: `mac_shortcut` runs a shortcut directly only if its name is in the app setting `macReadOnlyShortcuts` (`defaults write ai.wisp.app macReadOnlyShortcuts -array "Modo Foco"`, same agent-unwritable store, empty by default) and has no send/enviar/envia/message/mensagem/email/sms/mail word. The Shortcuts CLI cannot list a shortcut's actions, so nothing else is guessed: every other shortcut is refused and has to go through `mac_send` with `acao=atalho`, `app=Atalhos`, `to=[name]`, `subject=atalho`, `body=input text or the name`, which asks and then runs `shortcuts run`.
- `guard-outbound` (best effort, a barrier and not a lock). The helper is recognised by `Path(word).name == "wisp-mac"` or any path containing `Contents/Helpers` in command position of the shell-aware parser the email guard already uses (`_segments`, `_command_index`: wrappers such as `env`, `sudo`, `exec`, `command`, `timeout`; `bash -c` bodies up to depth 3; heredoc bodies; per-line fallback when quoting does not parse). It also blocks any command after a `cd`/`pushd` into a `Contents/Helpers` folder, an assignment of a helper path to a variable that is then used as a command, a command word with a `$` that is not a single plain variable (concatenation fails closed; `$WISP_BIN` and `$WISP_AGENDA_BIN` pass, a variable name containing `mac` does not) and a command word with `*` or `?`. `osascript` in command position (also `env osascript`, inside `bash -c`) with text that mentions System Events plus click, keystroke or key code, or JXA `ObjC.import` or `CGEvent`, is blocked when the text is inline (`-e`, heredoc), read from a file argument (`osascript f`, `-l JavaScript f`) or piped or redirected on stdin (`cat f | osascript`, `osascript < f`), the same three ways the email guard reads scripts; matching is on text with whitespace, quotes and parentheses removed, so a split application name (`"Sys" & "tem Events"`) gets through. Only shell script files named `.sh`, `.command`, `.bash` or `.zsh` are read for the helper rule.
- What still gets through, plainly. The deny patterns are glob matches on the command text; a free Bash shell can still write that plist or the callers folder through an interpreter, an encoded string or a variable, which is inside the accepted free-Bash limit below. A free Bash shell can still send through `osascript`, System Events or CGEvent (or a compiled binary or Python using Quartz) as a child of Wisp, because it inherits Wisp's Accessibility grant; the checks above only catch the common spellings. The server's default-deny and the approval card cover the `mac_*` tools, not the shell, and `guard-outbound` is a best-effort barrier, not a lock. Whether to confine the shell with a sandbox is a separate decision that has not been taken here. Also open: a shortcut or script that sends without send-like words in its name or text, a script assembled at runtime, a send control with an icon and no label, a messenger or webmail whose page matches none of the listed hosts or words, an app that sends on Return and is not in the safe list but that the user added, and keystrokes to a secure field made by `mac_script`. Under Codex the shell has no Accessibility (see the measurement below); under Claude Code it does.
- Permission modes: the read-only tools (`READ_ONLY`: apps, windows, tree, battery, wifi, dnd status, screenshot, shortcut list) are in the Claude `allow` list and need no card in the local engine; everything else follows the engine's mode (Claude Code: prompt in `default`, runs in `auto`/`bypassPermissions`; local engine: card in `default`). The watchdog message says that half-typed text may remain in the field.

## Self-learning

- Store: `<brain>/wisp/aprendizados.md`, a short heading and one line per lesson, `- <rule> · <YYYY-MM-DD> · <origin>`; only lines starting with `- ` count. Lessons are deduped by their rule folded to lowercase, no accents or punctuation (the first stays); past 40 the oldest are dropped (`wisp aprender add` prints a stderr line naming each). A rule with a token-like secret is refused; the rule is cut at 240 characters and the ` · ` separator inside it becomes ` - `.
- Capture: `wisp aprender add "<rule>" [--origem <text>]` (`já sabia` for a duplicate); the agent is told to call it by the hook text itself, with the absolute path of the running `wisp`, so no per-surface prompt changes. The `ask` permission rules (`Bash(*aprender add*)`, `confirmar`, `descartar`) in `harness/settings.json` and in the app's and bot's `--settings` make the engine prompt the user before any of the three runs; per the Claude Code docs an `ask` rule prompts even in bypassPermissions mode and wins over a user's own `allow`. `wisp setup` also removes the legacy `Bash(~/.local/bin/wisp aprender add:*)` auto-allow older installs carry (`REVOKED_ALLOW`). `wisp hook guard-lessons` (`PreToolUse`, same three settings, never in the harvest's) denies (exit 2) Write/Edit/MultiEdit/NotebookEdit on the active and pending lessons files and Bash commands that name `aprendizados` next to a write operator (`>`, `tee`, `sed -i`, `mv`, `cp`, `python -c`...); best-effort, a shell can always find another way. The brain harvest prompt has a step for the same lines (corrections and preferences only, facts stay in notes), but it writes them to `<brain>/wisp/aprendizados-pendentes.md`; right after the model child exits OK, `quarantine` puts the active file back exactly as it was before the harvest (the model can only add, an edited or removed active line is restored) and moves anything it left there into the pending file. The harvest runs under the scope guard and `wisp/` is inside the brain.
- Confirm: harvested rules wait in the pending file and the agent never sees them until the user runs `wisp aprender confirmar <n>` (or the app's Brain settings); `descartar <n>` drops one. Python and Swift both write the active file first and only then remove the pending line (a failed write loses nothing) and skip a rule already active (same folding as the dedupe).
- Use: `wisp hook aprendizados` (`SessionStart`, in the app's and bot's `--settings` and in `harness/settings.json`) prints the active rules (without date/origin) framed as preferences the user taught the agent, plus the `aprender add` instruction. No brain configured or any error: prints nothing, exit 0. Lessons saved during a conversation reach the agent from the next session start (a new conversation, or a resume), not the one that is running. The once-per-session marker (`aprendizados-sessoes/<session_id>`) stores a hash of the active rules, so a resumed session gets the text again only when the active set changed (for example after a confirm), never for pending ones. A session started under both `harness/settings.json` and `--settings` may receive the text twice.
- Undo: `wisp aprender listar` / `wisp aprender remover <n>`; the app's "O que o Wisp aprendeu" removes by line text (not by number), so a concurrent write never removes the wrong rule.

## Recall and brain harvest

- Recall (`wisp hook recall`): runs on every user message and never fails the turn (any error prints nothing). It searches the brain index with the message (same engine and ranking as `brain_search`) and injects only the strong head: a note qualifies when its title or aliases (not headings, which are full of generic words like "dia" and "semana") carry at least 35% of the message's rarity-weighted terms (each term weighs ln(1 + notes / notes containing it)) and that matched weight is at least 0.44 * ln(1 + notes in the brain) (about 3.5 in a brain of 2700 notes), and only the 10 best-scoring notes are considered (together these keep "bom dia, como foi o seu fim de semana?" and "oi tudo bem?" silent). A body-only match does not inject; the agent finds those with `brain_search`. Among qualifying notes the list stops at the first one scoring under 80% of the best, with a hard maximum of 8 notes; then one wikilink hop (outgoing and backlinks of the hits) is appended as compact entries ("ligada a [[x]]"). A neighbour is added only when at least 2 hits link to or from it, or when its own BM25 score for the prompt is at least 25% of the best hit's; the count is capped at 2 per hit and 8 in all, most-linked first. `recall_tokens` in `wisp.json` (default 6000, clamped to 500..50000; tokens estimated as characters / 4, header included) is only a ceiling: an entry that does not fit is skipped. Each entry is `- [[link]] (path) — title`, the TL;DR or first paragraph (800 chars) and the best matching passage (300 chars). The header frames the notes as reference data, not instructions, and tells the agent to call `brain_search`, `brain_read` and `brain_links` freely and to cite the notes it used as `[[wikilinks]]`. A hit is offered once per session. A neighbour shown only as a link is remembered separately: it is not repeated as a link, but it can still come back later as a full entry if it becomes a hit. Only regular files inside the brain are read (a FIFO or a symlink that leaves the brain is skipped), at most 64 KiB of each. The index sync inside the hook stops after 3 s; while the index is still incomplete (the first build of a very large brain finishes over the next messages, or another process holds the write lock and no full build has ever finished, tracked by a `complete` flag in the index) recall injects nothing rather than rank on a partial index; with a lock held and a complete index it uses the existing one. It waits at most 1 s for the index lock. `WISP_RECALL_OFF=1` makes it print nothing (the harvest child sets it).
- Brain search (`wisp mcp brain`, server `wisp-brain`, tools `brain_search`, `brain_read`, `brain_links`): read-only MCP tools registered for every engine: in Claude by `wisp setup harness` (`claude mcp add --scope user wisp-brain`, tools pre-allowed, a foreign server of that name is left alone), in the Codex `config.toml` block (a user-defined `wisp-brain` stays and ours is left out; same for `wisp-email`, independently), and as a trusted built-in server of the local engine (name and tool names reserved, tools read-only so `default` mode does not ask). The brain is `brain` in `wisp.json`; with none configured (or the folder missing) the server still starts and each tool answers that the brain is not configured, so the local engine does not report a server that failed to open. Both Codex hosts (the app's `CodexCommand.mcpOverrides` and the bot's `codex_runner.mcp_overrides`) pass `wisp-brain` as `-c` overrides after `wisp-email` on every launch, pinned by `cli/tests/fixtures/contract/codex-mcp-overrides.json`, except when the user owns a `wisp-brain` of their own: `wisp codex check` now also prints `owned` (the `wisp-email`/`wisp-brain` tables defined in `config.toml` outside the Wisp block, any TOML form); the bot reads that file itself, and the app takes `owned` from the same `wisp codex check --workspace` run its preflight already does before each turn (one process per turn; if that check fails Codex does not run and the turn falls back to Claude, so a failed check never means "send the override"), and the user's server is then left alone. `wisp-email` is always overridden, on purpose: the send gate must be Wisp's server, and `codex check` already refuses to run when a user-owned one does not forward the approval socket. The two servers are independent in `config.toml` too: the Wisp block carries the brain even when the user owns `wisp-email`, and the reverse. A user config with an inline `mcp_servers = { ... }` table cannot take a second table (nor can one that would not parse after the merge): the sync tries the email table alone, then no Wisp block at all, leaves `config.toml` untouched, reports "(inline table)" and still writes `AGENTS.md`; a user-owned inline `wisp-brain` is treated the same way. If the email server then is missing, the usual stale-gate failure still applies and Codex stays off.
- Index: a SQLite FTS5 file per brain root under `<state>/brain-index/` (no service, no network). Columns title (H1 or filename, plus the filename words), aliases, headings and body (first 128 KiB), weighted 10/8/4/1 in `bm25`, with diacritics folded and words of 4+ letters matched by prefix (words of 6+ letters by the first n-2 letters, a crude plural/inflection stem). Links and file stamps live in the same file. Every call walks the folder and compares `(mtime_ns, size)`; only changed files are re-read, deleted ones are dropped, and a file SQLite reports as corrupt or not a database is deleted and rebuilt, but a busy or locked file never is. The schema check and migration run inside one `BEGIN IMMEDIATE`, and a process that waited for the write lock re-reads which files are stale before indexing, so concurrent processes index each file once. A `.md` with a NUL byte in its first 8 KiB is binary: it is recorded (so it is not re-read) but never indexed or readable. A read error (permissions, an iCloud placeholder, a file that vanished) records nothing, so the next sync retries it. Skipped: `.git`, `.obsidian`, `.trash`, `arquivos`, every folder whose name starts with a dot (so `.claude/coordination/...` logs stay out), hidden files, non-`.md`; a symlinked directory is not followed and a symlinked file counts only when its real path is inside the brain (checked again at read time). With the write lock held past the wait, the sync is skipped and the existing index is used. In the MCP server any SQLite error becomes one tool error sentence ("o índice do brain está ocupado ou danificado agora…").
- Ranking: `score` = (BM25 divided by the best hit's, so the top is 1, + graph boost + in-degree prior + canonical bonus) * log factor. Graph boost: 25% of the normalized score of each of the 10 best lexical hits that links to or from the note, capped at 0.5. In-degree prior: up to 0.15, reaching the maximum at about 20 inbound links (log scale). Canonical bonus: 0.3 * the share of query terms found in the note's title, filename or aliases, plus 0.1 when frontmatter `status` is `active`. Log factor: 0.4 for log-like notes, so a session transcript never beats the topical note it came from. A note is log-like when a folder in its path (any depth) or one of its frontmatter `tags` equals a marker; the markers are `brain_log_markers` in `wisp.json` (default `sessions`, `daily`, `digest`, `session`, `log`; compared without case or accents; an empty list turns the demotion off). Only the 100 best lexical (BM25) candidates are re-ranked; the graph never adds a note that did not match. BM25 weighs terms by rarity, so in a brain of a few notes most words weigh about zero and the ordering falls back to the field weights.
- Wikilinks resolve like Obsidian: file name without `.md`, case-insensitive; then frontmatter `aliases`; then the note title; a path (`folder/note`, any suffix of the real path) matches by path. `#heading`, `#^block` and `|text` are accepted and split off; `[[#heading]]` points at the note itself; embeds of attachments (png, pdf, ...) and anything inside code fences or inline code are not links. With several candidates the one in the source note's folder wins, then the shallowest path. A name with no case-insensitive match is retried with accents folded. A link that resolves to nothing stays in the list with no path (a broken link). `brain_read` also takes a path, an absolute path inside the brain, or a title; a path outside the brain resolves to nothing, and a miss answers with the closest notes. A `#heading` returns only that section (to the next heading of the same or higher level), or the whole note with `heading_found: false`. `brain_links` walks outgoing links and backlinks to depth 1..3 (at most 100 nodes) and lists the broken links it saw.
- Harvest (`wisp brain colher`): a conversation is eligible after 30 min without messages and with at least 3 user messages since the last harvest. A ledger (`colhidos.json` in the state dir) keeps the transcript offset already summarized per session, so a later harvest reads only what is new. Sessions in use or whose Telegram topic is closed are skipped. The model child runs with `WISP_BRAIN_SCOPE` set to the brain root and a second PreToolUse hook, `wisp hook guard-brain-scope` (only in the harvest's own settings), which denies Read/Write/Edit/MultiEdit/NotebookEdit/Glob/Grep on any path (`file_path`, `notebook_path`, `path`, or the cwd when Glob/Grep have none; symlinks resolved) outside the brain, and Glob patterns that are absolute or climb out with `..`. Without the env var the guard allows; any error in it blocks.
- One run at a time machine-wide (global lock); `--if-due` skips when the last run was under 10 min ago, so the app and the bot can both call every 10 min without doubling work. Conversation text is never logged: callers log only counts of harvested and skipped.
- The switch is `brain_learn` in `wisp.json` (default true, Settings > Geral > Brain). Off means the command reports one skipped entry and does nothing.
- App side: `BrainColherScheduler` ticks at launch +2 min then every 10 min and never overlaps ticks (each awaits the previous); the CLI run lives off the cooperative pool since it can last minutes. The app reads only the two list lengths of the `--json` report, never the conversation names. `WispConfigFile` edits single keys of `wisp.json` and leaves the rest (the CLI owns the schema), refusing a symlink; choosing the brain folder also moves `blocks.memory.root` of `profile.json` (and `blocks.tasks.file` when it still pointed at the old `pendencias.md`), and writes nothing when the profile is missing, a symlink or not a regular file.

## Wisp folder and email

- `~/Wisp/` (`WispConfig.wisp_dir`) is the agent's source: `agente.md`, `guardrails.toml`, `modelos.toml`, `skills/`, `ferramentas/`, `conversas/`. `wisp setup folder` seeds only what is missing and never overwrites a file; a brain configured elsewhere is referenced in place, never moved or copied. `wisp harness sync` renders the folder into `~/.claude`: the `agente.md` body replaces the block between `wisp:begin/end` (only known `{{KEYS}}` are substituted, the rest stays verbatim) and `skills/` is installed with the same manifest as before.
- `wisp mcp email` is a stdio MCP server (`wisp-email`) over the macOS Mail app through `osascript -l JavaScript`; arguments travel as JSON in argv, never inside the script. Mail closed, Automation denied (-1743) or a 30 s timeout come back as one pt-BR sentence, never a traceback. `harness sync` registers the server with `claude mcp add --scope user` once and adds the three read tools (`mcp__wisp-email__email_list`, `_read`, `_search`) to `permissions.allow`; `email_send` is never allowed, it has an `ask` rule (next bullet).
- Sending mail is approved by Claude Code's own permission prompt, never by the tool: `permissions.ask` holds `mcp__wisp-email__email_send` in `harness/settings.json` and in the engine `--settings` the app (`EngineGuards.settings`) and the bot (`claude_runner.guard_settings`) pass to every `claude`; the contract fixture `cli/tests/fixtures/contract/guard-settings.json` pins it for both. An `ask` rule prompts in every permission mode (checked 20/11/2026 on Claude Code 2.1.329: `-p --input-format stream-json --permission-prompt-tool stdio --permission-mode bypassPermissions` with `permissions.ask: ["Bash(touch probe*)"]` produced a `can_use_tool` `control_request` for `Bash`, init `permissionMode: "bypassPermissions"`; the same with `--mcp-config` for `wisp mcp email` produced one for `tool_name: "mcp__wisp-email__email_send"` with `permission_suggestions: null`; both were answered with deny and nothing ran). The prompt is answered by the host process on the stdin of `claude`, which the agent cannot write, so unlike the file channel it replaced (`~/.local/state/wisp/approvals/<id>.decision`, forgeable by any same-user process that could read the request's nonce) the answer cannot be forged from inside the session. **`email_send` itself also asks the host before it sends, under every engine, and there is no switch that turns that off** (changed 20/11/2026 after a review: the old `WISP_SEND_GATE` variable, whose absence meant "no gate", let an agent run `WISP_SEND_GATE= wisp mcp email`, talk MCP to its own copy and send with no click). The tool sends only after the host behind the Unix socket in `WISP_APPROVAL_SOCKET` answers allow. Under Claude the host (the app's `AgentSession`, the bot's `claude_runner._turno`) opens that socket for the conversation or turn, sets the path in the env of `claude`, and, when it answers `allow` to the `can_use_tool` of `mcp__wisp-email__email_send`, first mints a single-use ticket in its own memory: sha256 of the exact input (`to`, `cc`, `subject`, `body`; a missing `cc` counts as empty; each string as `<utf8 length>:<bytes>`, lists as `<count>[...]`, the four fields joined by `\n`; the same bytes in `bot/src/wisp_bot/broker.py` and `ApprovalBroker.fingerprint`, pinned by the `ticket` vector in `cli/tests/fixtures/contract/approval-broker.json`), valid 120 s on the monotonic and the wall clock. The email server then sends `request` with its input; the host consumes a ticket with that exact hash and answers allow, or answers deny ("não há aprovação para este e-mail exato"). A request for different content, a second send of the same mail, an expired ticket or a user's Negar get no ticket. A Claude broker has no live card (`live: false`), so the model cannot make the host raise one. The socket has one verb, `request`: nothing on it mints or answers anything, so the agent knowing the path (it is in its own env) gains nothing. With no host reachable nothing is sent, and that includes a terminal session of `claude` or `codex` the user starts without the Wisp app or bot (no socket in its env: the tool answers "não enviei: ... canal de aprovação ... não está disponível aqui"). Measured 20/11/2026 on the installed Claude Code (`claude -p --strict-mcp-config --mcp-config <scratch>` with a scratch stdio MCP server that returns `os.environ.get("WISP_APPROVAL_SOCKET")`, run with `WISP_APPROVAL_SOCKET=/tmp/host-set-socket` set only in the parent): the server printed `SEEN='/tmp/host-set-socket'`, so Claude Code passes the host's env to stdio MCP servers (the real `wisp-email` registration has no `env` block of its own). Residual: an agent that reaches the socket with its own copy of the tool and the exact content the user just allowed can spend that one ticket, which only sends the mail the user approved, once. The broker accepts only a peer whose uid is the host's (`getpeereid` in Swift; `SO_PEERCRED`/`getpeereid` in the bot) and keeps at most one live card open per broker (extra requests are denied at once with "já existe um pedido aguardando"). The app shows its normal approval card ("Sempre permitir" is hidden for this tool: `PermissionRequest` drops the `addRules` suggestions for `EngineGuards.askTools`; an `ask` rule would beat the saved allow anyway). The Telegram bot runs claude with `--input-format stream-json --permission-prompt-tool stdio`, sends the user message as a `user` line, answers each `can_use_tool` with a card (Permitir/Negar, only the configured owner; 600 s without an answer denies; a `control_cancel_request` or the end of the turn closes the card) and writes the `control_response` line itself; a turn without a handler (or a handler that raises) denies. A request too long for a Telegram card (4000 characters after HTML escaping) gets no Permitir button and is denied at once with "aprove pelo app" (the bot's claude process is not the app's, so the app cannot answer it: the model is told to ask the user to do it in the app). Recipients must each be one plain address (no commas, semicolons, spaces, newlines or `Name <addr>`), checked before the send. `guard-outbound` keeps only the best-effort check that Bash does not send mail around the tool (osascript/JXA through Mail, Python importing `wisp.email`); it no longer looks at the approvals folder or at the content of scripts being written. Not verified at runtime: a real Telegram card (the bot code is tested against a fake `claude` and a fake Telegram, not a live bot), the app card for `email_send` (Swift tested, app built but not driven), and the turn timeout (900 s default) running while a card waits.
- `wisp config set wisp_dir|brain <path>` saves the path, moves nothing and runs `harness sync`; Ajustes > Geral has the "Pasta do Wisp" row (the brain folder control is a separate change).
- Sending around the tool, best-effort only: `guard-outbound` also refuses Bash that runs `osascript` with a Mail script that sends (`tell application "Mail"`/`Application("Mail")` with `send`, `OutgoingMessage`; the `-e` text, heredocs and script files named on the command line are read; quotes, `+`, commas and brackets are squashed so `Application('Ma'+'il')` still matches) and Bash that runs `python` with `wisp.email` or `MailApp`. It is a deterrent, not a sandbox: an encoded or downloaded script, another mail client (`sendmail`, `curl` over SMTP) or a script written in a way the patterns do not see still gets through. The real gate is the `ask` rule on `email_send`; a script that skips the tool skips the prompt too.
- `wisp harness sync` never follows a symlink inside `~/Wisp/skills`, so a link there cannot copy files from elsewhere into `~/.claude`.

Runtime, venv, uv cache, bundled Ollama app and the Python install: `~/.local/share/wisp/`. App state that is not the user's content: `~/Library/Application Support/Wisp` (`settings.json`, `setup.json`, `conversations.json` index), `~/.config/wisp` (`wisp.json`, `profile.json`, `pair.conf`), and `~/.local/state/wisp` (bot state, ctl queue, locks, guard settings, `aprendizados.lock`). Locks and sockets stay in state or temp. Models already downloaded by Ollama stay in its own store (`~/.ollama/models`): it is shared with other tools and holds multiple GB, so Wisp does not move or repoint it.
- Migration (`wisp folder migrate`, also run by `wisp setup folder`; the app runs it at every launch after the runtime is ready) only moves small things: the entries of `~/Library/Application Support/Wisp/anexos` and `<state_dir>/anexos` into `anexos/`. A same-volume move is an instant rename and always proceeds. Only when the rename fails with EXDEV is the copy checked against the caps: an entry over 256 MiB, or past a 1 GiB budget per run (counted only for what is actually copied), stays where it is and is reported (`left`, logged once as `ficou`). Recordings never move on their own: when `wisp_dir` changes, Ajustes > Geral offers "Mover reuniões" (`wisp folder migrate --reunioes`), which has no size cap or timeout, prints one `{"type":"progress","done","total","item"}` line per entry and can be run again to finish what a first run left. The recordings move refuses while a recording is active (a `meta.json` with `status: recording` in a folder touched in the last 60 s, the same marker the recorder writes) and leaves any entry modified in the last 60 s in place (`modificada há pouco`); Ajustes disables "Mover reuniões" under the same rule. An old folder that is itself a symlink (for example `anexos` pointing to an external disk) is skipped and reported, never followed, moved or deleted. Relative symlinks inside a moved tree are rewritten after the move so they still resolve (links inside the entry or its sibling entries follow the move, links to anything else are re-pointed relative to the new place). Folder identity is `samefile` (device and inode), not the path text, so `~/wisp` and `~/Wisp` are one folder on a case-insensitive volume. A pair of folders where one is inside the other (for example `wisp_dir` set to `~/Wisp/reunioes`) is skipped and reported, never moved.
- Each entry moves with an atomic no-overwrite rename (`renamex_np` with `RENAME_EXCL` on macOS, the helper of `arquivos.py`; `link` + `unlink` for files and an exclusive `mkdir` for directories elsewhere; on a volume that answers ENOTSUP, such as exFAT, SMB or NTFS, directories are an exclusive `mkdir` followed by moving the children, and files are `link` + `unlink`, or an `O_EXCL` create plus copy when hard links are refused), so a destination that appears at any moment is a conflict, never overwritten: both stay and it is reported. Across volumes it copies to `.wisp-part-<name>` in the destination with `F_FULLFSYNC` (plain `fsync` where unavailable) on every file and every directory, renames it into place, and only then deletes the source without ignoring errors; if the source cannot be fully removed the item is reported as failed with the reason (`parcial` in the log) while the copy stays. A leftover `.wisp-part-*` is removed on the next run. A crash between the final rename and the delete of a cross-volume copy leaves the item in both places; the next run reports a conflict instead of guessing.
- The log (`logs/migracao.log`, lines `<time> <moveu|conflito|ficou|pulou|falhou|parcial> <detail>`) is appended and fsynced as each item finishes, so an interrupted run still shows what happened. `MOVIDO.txt` is written in an old folder only when at least one item moved out of it and lists only the moved items. A cleanup error on a destination is reported as a failed pair, not fatal. `profile.json` `blocks.telegram.attachments` is rewritten when it still names an old attachments folder.
- Default brain: with no `brain` key in `wisp.json`, a `~/Wisp/brain` with at least one `.md` file (ignoring `.git` and `.obsidian`) is kept (the path is written into `wisp.json` once) even when `wisp_dir` points elsewhere, so an upgrade never leaves an empty brain; otherwise the brain defaults to `<wisp_dir>/brain`.
- The bot never imports `wisp`, so it does not migrate: it resolves the new folders at import and an update leaves the old ones for the next `wisp folder migrate` (app launch or setup).

## Conversation transcript

- Format (v1, `cli/tests/fixtures/contract/conversation-transcript.jsonl`): one JSON object per line in `<wisp_dir>/conversas/<conversation>.jsonl`, keys sorted, no spaces, UTF-8 unescaped, timestamps UTC with milliseconds. Kinds: `session` (`session`, `engine`, `reason` new or rebuilt: links an engine session id to the conversation), `user` (`surface` app or telegram, `text`) and `assistant` (adds `engine` and `model`, the model the CLI reported in its init event). Only the typed message and the final reply text are stored: never tool calls, tool output, file contents or the bot token (the bot replaces its own token with `[redacted]`). The Swift app (`TranscriptStore`) and the Python bot (`wisp_bot.transcript`) both write it, test each other's bytes through the fixture, and take `flock(LOCK_EX)` on the file for each append, so a line is never interleaved; a last line left half-written by a crash is closed with a newline before the next append. Files are `0600`.
- Identity: the conversation of the app and of a Telegram topic is already one thing through the Claude session id (`TelegramTopics.topic(forSession:)`, `compartilhar`). The transcript file is named after the first id the conversation had: the session id for a conversation that starts on Telegram, the app's conversation UUID (lowercase) for one that starts in the app, because the session id does not exist until Claude answers. Every later session id is linked by a `session` line, and both sides find the file by name first, then by scanning for that line. A reset (the Geral every 24 h) keeps the conversation: its new session id is linked with `reason: reset` (see "One conversation, one id").
- Rebuild: the engine session is a cache. The bot treats `claude` exiting with "No conversation found with session ID" as a lost session (`Result.resume_failed`, stderr or the result's `errors`); it also primes when it would start a fresh session for a conversation that already has history. The app does not guess from the session file's location (Claude may keep it under `$CLAUDE_CONFIG_DIR`): it always tries `--resume` and reacts to that same error on the running process, re-sending the prompts that were in flight. A conversation counts as having history only when the transcript holds at least one assistant reply, so a first turn that failed is never reported as a lost session. A rebuild starts a new session (new id, linked in the transcript, turns and cost of the topic kept) and prepends to the prompt a memory block: the last 6 messages up to 3000 characters each, older ones up to 400, 24000 characters in all, oldest dropped first; no model call. Without any transcript there is nothing to rebuild and the error shows as before.
- Writes fail open: the error is logged, the answer is delivered, and one notice per app run (app) or per bot run (Telegram) says the folder could not be written.
- A conversation whose session was rebuilt on one side has a new session id there; the link is the conversation id, so the other surface keeps the same conversation (see "One conversation, one id" under Engine interface).

## Engine interface

- One shape on both sides, small on purpose; the local engine (plan 4) plugs into the same one. **Swift** (`core/Sources/WispCore/Engine/EngineSession.swift`): `EngineSession` has `kind`, `events` (`AsyncStream<SessionEvent>`), `start()`, `send(_:)`, `respond(to:_:)`, `stop()`, `processIdentifier` and `routesApprovals`. "Resume" is the `resume` value of `EngineLaunch`; `EngineFactory.make` builds `AgentSession` (Claude, one long-lived process fed through stdin) or `CodexSession` (one `codex exec` process per turn behind the same stream). Every engine speaks the one conversation format the app renders: the engine adapters emit `ClaudeEvent`s (the name is historical; it is the shared event type) and the reducer never learns which engine produced them. The thread an engine assigns to itself travels as `ClaudeEvent.engineSession(engine:id:)`, is written to the transcript as a `session` line with that engine, and never replaces `ConversationState.sessionId`, which stays the conversation's identity. **Python bot** (`wisp_bot/engine.py`): `Engine` has `name`, `run(prompt, *, session_id, cwd, started, ...) -> Result` and `status() -> Status`; `Result` carries `engine` and `model` for the turn (written to the transcript). `session_id` is the id Wisp chose for Claude (`--session-id` / `--resume`) and the saved thread id for Codex, which assigns its own: `Result.session_id` is what to pass back next time. The bot has no in-turn approval channel of its own (its permission mode is fixed per turn); Claude turns pass `on_permission` (the `can_use_tool` card) and Codex turns pass the same callback to the email approval broker (`Engine.run(..., on_permission=...)`), so the bot answers email approvals for both engines with the same Permitir/Negar card. `respond` exists only on the Swift side, where `routesApprovals` says whether the engine routes the CLI's own tool approvals (Claude yes, Codex no); `CodexSession.respond` answers only the email broker's requests and throws `approvalsNotRouted` for any other id.
- Active engine: `ativo = "claude" | "codex"` at the top level of `<wisp_dir>/modelos.toml` (a key inside a `[table]` is ignored). One writer, `wisp config set engine <name>` (seeds the folder, writes the line and keeps the rest of the file, then syncs Claude and Codex rendering); readers are the app (`EngineChoice`) and the bot (`engine.active_name`); a missing, unreadable or unknown value means Claude. The file is per machine because the Wisp folder is local; nothing syncs it. Plan 4 adds more engine names and picks them in the full Modelo tab.
- Engine not usable on this machine: the app (`CodexReadiness`, `codex --version` and `codex login status`, exit 0 means logged in) and the bot (`engine.resolve`, status cached 30 s) run the turn on Claude and say so (a system line in the app, an italic note in Telegram). It is decided per turn, so installing or logging in takes effect on the next message.
- Switching engine in the middle of a conversation reuses the rebuild path of "Conversation transcript": the engine that answered the last reply (transcript `assistant` entries carry `engine`) is compared with the one about to answer; if they differ, or the new engine has no saved session, it starts a fresh session primed with the same memory block (last 6 messages, 24000 characters) and a one-line note names the engine ("↻ agora quem responde é o Codex; ele retomou pela conversa guardada no Wisp."). A Claude switch-back starts a new Claude session id (linked as `rebuilt`), exactly like a lost session. A Codex thread id is stored as a `session` line with `engine: codex` and resumed with `codex exec resume <id>` while Codex keeps answering; a resume that fails before any `turn.started` is treated as a lost session and rebuilt. A conversation that starts under Codex has **no `sessionId`** in the app (that field is only ever a Claude session id; nothing invents one): its identity is the conversation UUID, which is the transcript file name, and each engine only resumes its own id (`EngineResume.plan`: Codex never gets a Claude id, Claude never a Codex thread). The app reads history by that conversation id from Wisp's transcript whenever there is no Claude session or any reply came from another engine, because Claude's own session file only holds Claude's turns (`TranscriptHistory.load`). Sharing such a conversation to Telegram stays unavailable until a Claude turn gives it a session id.
- Resume rules (`EngineResume.plan`, core): each engine only ever resumes its own session id, so a Codex turn never sees the Claude id and a Claude turn never sees a Codex thread. A different engine than the one that answered last, a session that is gone, or one the engine never had means a fresh session primed from the transcript. A Claude conversation with no session id is now primed from the transcript instead of starting blank, and history falls back to the transcript.
- Safe folders: `safeDirectory` / `safe_dir` return the resolved path of a directory that is not home, a parent of home or `/`, else nothing; `workspace` is the conversation's folder when safe, else the Wisp folder when safe, else nil, and then the turn does not run on Codex. `TranscriptHistory.load` shows Wisp's transcript when any reply came from an engine other than Claude or when there is no Claude session (a Codex-only conversation, found by its conversation id), otherwise Claude's session file with the transcript as fallback. `engine.resolve` returns the engine for the turn and the note to show when the active one is unusable here. `sync_codex`'s merge reports added, updated, unchanged or conflict, and the digest to record. `EngineModel` (Ajustes > Motor) only reads `modelos.toml`; `wisp config set engine` writes it and renders Codex's files.
- One conversation, one id (`OneConversationTests`, `bot/tests/test_conversa_sync.py`): the Wisp conversation id (lowercase UUID, the app record `id`, the transcript file name) is the key; the topic stores it (`Topic.conversation`, `TelegramTopic.conversation`) and `TelegramTopics.topic(forSession:conversation:in:)` matches it first, then the session id (legacy topics and any record pointing at the same live session). A topic created on Telegram gets a UUID from the bot; one shared from the app takes the app's id (`--conversation`); an older topic is backfilled with `transcripts.find(session) or session` and a mirror cursor of "now" (history is not replayed). A topic opened in the app with no record creates one with `id = UUID(conversation)`. Session ids are a cache: `conversa.garantir` links the topic's current session to the conversation file at each turn and on `/reset` (`reason: reset`, which is also a memory boundary: `build_context` / `ConversationTranscript.context` ignore everything before the last reset, the app still shows it). The app adopts the topic's session before a turn when the topic has turns, and a followed conversation prepends the transcript's messages from before the followed session's link.
- Offline catch-up (`conversa.alcancar`): the transcript is the queue. Entries with `surface: app` after the topic's `espelhado_ate` are posted in order (a header when there are several exchanges or the first one is older than 90 s; with several, only the last 5 and each reply cut at 1200 characters); the cursor moves after each exchange, so a send that fails midway resumes without repeating. The app's `postar` carries `conversation` and the bot answers it with the same catch-up (a failed request is not lost: the next 15 s tick posts it); a topic with no cursor gets one set to now and replays nothing.
- `wisp topic unir`: see the CHANGELOG. Not an automatic migration: run the plan, close the app, stop the bot, then `--aplicar`. A conversation file named after a session id (older Telegram-born topics) next to the app's own UUID-named file is joined by the same command.
- Known limits of the one-conversation link, left as they are: (1) an older Telegram topic whose transcript is named after its session id, next to the app's own UUID-named file, keeps two transcript files until `wisp topic unir` joins them; (2) the legacy id of a topic without `conversation` is the app record that points at its session, so a topic whose Geral already reset on the old code (app record and topic session no longer equal) is not linked by the backfill and needs `wisp topic unir`. A mirror request from an app that does not send `turn_at` is posted from its payload whenever the catch-up found nothing, which can repeat a turn the periodic catch-up posted a moment earlier.
- Known limits, display and locking: (3) `TranscriptHistory.merge` cuts the Claude messages at the first match of the first Wisp message of a session; if that text is common (like "oi") and also occurs earlier in the Claude file, the messages in between are hidden. Display only, nothing is lost on disk. (4) `store.file_lock` blocks inside the bot's asyncio loop while another process holds it; the wait is bounded by the length of `wisp topic unir --aplicar` and only matters with `--forcar`, because without it `unir` refuses while the bot runs.
- `coberto` decides "already posted" by the exact transcript entry: the app sends the `at` its reply got in the transcript (`turn_at`), and a mirror is skipped only when an app reply with that `at` and that text sits at or before the topic's cursor; an identical reply text (a repeated "Feito.") never counts. A record `unir` keeps because its Claude file is not on this Mac gets a `pending-import` link and is left out of later plans until the file appears, so a second run with nothing new prints "nada para juntar" and takes no backup.

So the server can connect to a socket outside the writable roots. **What the sandbox lets the agent's own commands do.** macOS (`sandboxing/src/seatbelt.rs`, `seatbelt_base_policy.sbpl`): the base policy starts with `(deny default)`; Unix sockets are allowed only by `unix_socket_policy`, which returns an empty policy unless an allowlist (`network.allow_unix_sockets` from managed network config) or allow-all exists: `if !has_unix_socket_access { return String::new(); }`, and with network off (`!network_policy.is_enabled()`) and no allowlist `dynamic_network_policy_for_network` returns `String::new()`, so there is no `system-socket AF_UNIX` and no `network-outbound (remote unix-socket ...)`: a sandboxed command cannot even create or connect to the broker socket. Apple Events: the only `mach-lookup` allows are `com.apple.system.opendirectoryd.libinfo`, `com.apple.PowerManagement.control`, the cfprefsd names, the platform-defaults list (analyticsd, appsleep, bsd.dirhelper, diagnosticd, `com.apple.dt.automationmode.reader`, logd, secinitd, trustd, ... none of them AppleEvents, launchservicesd or Mail) and, only with network on, configd/trustd/ocsp names; `(deny mach-lookup (xpc-service-name-prefix ""))` is appended last. So `osascript`/Apple Events to Mail from inside the sandbox is denied by default-deny; measured, see "Codex sandbox probe" below. Linux (`linux-sandbox/src/seccomp.rs`): in `NetworkSeccompMode::Restricted` `deny_syscall(&mut rules, libc::SYS_connect)` (and `bind`, `listen`, `accept`, `sendto`); `socket`/`socketpair` stay allowed for `AF_UNIX` only, and bwrap adds `--unshare-net` (`bwrap.rs`), so a sandboxed command cannot connect to a Unix socket either. **Residual risks (honest list).** (1) Under Codex no mode passes `--approve-for-me` or any escalation, so Automático and Sem pedir are both `workspace-write` with `approval_policy: Never`; the hole where an auto reviewer approved a command outside the sandbox is closed by construction, but it rests on Codex `exec` honouring that policy (read from source, not run). (2) Inside the sandbox the agent can still spawn `wisp mcp email` itself (the sandbox allows `process-exec` and full-disk read in read-only), but its copy has no socket it can reach (a sandboxed command cannot connect to one) and cannot send mail without Apple Events, and the probe below measured both as denied under the policy built from Codex's own `.sbpl` files; that is a property of Codex's sandbox on macOS, not something Wisp enforces, and it was measured against a hand-assembled policy, not against a running Codex. (3) The gate protects `email_send`; Codex's shell in "Automático"/"Sem pedir" can write any file the sandbox allows, and `guard-outbound` does not exist under Codex. (4) The card shows what the tool is about to send, but the same-user MCP process builds it: a modified `wisp` binary or Python environment (not writable from the sandbox) could lie. (5) The request is not tied to a single use beyond the connection: the host answers each connection once, and a card answered after the client left is refused (`answer` returns false), but the user can still approve a request that an attacker-controlled prompt injection wrote, because the card shows the real recipients and body and the click is the control. (6) `env_vars` forwarding and the gate under a real Codex were not run.
- Approval socket authenticity (#14, hardening after review): the client no longer trusts a socket only for its owner and folder mode, because the agent can bind its own `0700` socket that answers allow and run `WISP_APPROVAL_SOCKET=<own> wisp mcp email` as its own MCP client (the environment is visible to its shell, so a secret in env would not help). After `connect` and before sending anything, `send_gate._check_host` takes the server's pid from the kernel (`LOCAL_PEERPID` on macOS, `SO_PEERCRED` on Linux) and requires (a) that pid to be a strict ancestor of the email server process (ppid chain: `proc_pidinfo` `PROC_PIDTBSDINFO` on macOS, `/proc/<pid>/stat` on Linux) and (b) its executable (`proc_pidpath` / `/proc/<pid>/exe`, realpath) to be the Wisp app binary (`/Applications/Wisp.app/Contents/MacOS/Wisp` or `~/Applications/...`) or a python of the Wisp runtime (`~/.local/share/wisp/runtime/venv/bin/python*`, resolved, plus the framework `Python.app` binary a venv python resolves to). Both lists come from fixed install locations and the passwd home, never from env (`HOME`, `XDG_*` are not read); an unreadable pid, chain or path refuses (`não enviei: ... canal de aprovação ...`). Cost: a Wisp installed elsewhere, or with `XDG_DATA_HOME` moving the runtime, refuses to send mail until moved (fail closed). `guard_outbound` (Claude only) also blocks a Bash command that starts the email server (`wisp mcp ...`, `python -m wisp ... mcp`, the runtime's `wisp` with `mcp`) or mentions `WISP_APPROVAL_SOCKET`. Not covered (honest residual): the runtime's python is the host key, so any script that interpreter runs can act as a fake host (bind its own socket as an ancestor of its own `wisp mcp email`). Only `guard_outbound` stands in the way, and obfuscation beats the guard. What the guard sees now: the Bash command string and the contents of the files it runs, namely the first file argument of osascript, python (any version, the runtime's included), node, ruby, perl, bash, sh and zsh, plus files in the command with a script suffix; on those texts it looks for `wisp mcp` as a whole word (also in list form), `-m wisp ... mcp` and `WISP_APPROVAL_SOCKET`, and for mail sends. An interpreter counts only in command position (start, after `;`, `&&`, `||`, `|`, `(`, a newline, or after `env`, `sudo`, `exec`, `nohup`, `timeout N`, `xargs`, `command`, `time`); each interpreter has its own flag tables (python: value flags `-W -X --check-hash-based-pycs`, `-I`/`-E` plain, `-c` cluster inline, `-m mod`/`-mmod` reads `./mod.py` and `./mod/__main__.py` in the command's cwd, dotted names as path segments; shells: `-c` cluster inline, `-o`/`+o` take a value; perl `-e`/`-E`, ruby `-e`, node `-e`/`-p`/`--eval`/`--print`, osascript `-e` are inline, and the value flags of each are skipped) and inline code reads no file; `#` is never a comment for the guard's tokenizer (a stray quote in a comment fails closed); `< file`, `cat file | interpreter` and `uv run [python] file` read that file. A file that exists but cannot be read, or is over 1 MB, is blocked; a missing file is ignored. Residual: a module found elsewhere on `sys.path` (not the cwd) is not read; other readers feeding an interpreter (`tail`, `sed`, `curl ... |`, process substitution, `-` with a here-string of a file's contents) are not followed, nor interpreters behind other wrappers (`nice`, `ssh`, `docker`, `find -exec`). It does not see code built at run time (string concatenation, `eval`, `exec`, base64, a file the script writes and then runs, an `import` of another module that does it). Under Codex there is no guard at all and the sandbox has no Unix sockets, so this is Claude-side only.
- Design boundary, not a security boundary (#9 and #14): with a free Bash under the user's uid the email approval gate stops the assistant from sending by mistake or by a plain tool call; it does not stop a hostile or prompt-injected agent. `guard_outbound` is a best-effort filter (it now also reads any file given to `osascript` and blocks one it cannot read, `open mailto:`, `wisp mcp email` and `WISP_APPROVAL_SOCKET`), but obfuscated osascript (built strings, `eval`, scripts written at run time, `osascript` through another interpreter) can still send mail. The real fix is a sandboxed shell for the agent (no Apple Events, no sockets, no process spawn of its own host), a separate front not in this PR. Also known and left unchanged (not trivial to close): the agent can use an approval the user gave early, since it is the one that decides when to call the tool again after the card is answered; the approved request is what is sent, nothing the user did not see.

## Local engine

- Unit: `cli/src/wisp/local/` (not wired into the app or the bot yet; plan 3 owns `ConversationRuntime.swift`, `claude_runner.py` and `ClaudeCommand.swift`). Run it on its own with `wisp local chat --message TEXT [--conversation ID] [--model TAG] [--mode default|auto|bypassPermissions] [--surface app|telegram] [--thread N]`; `wisp local catalog|pull TAG|install-ollama|use TAG` feed the picker. Every command prints one JSON object per line and exits 1 with `{"type":"error","message":...}`.
- Seam for plan 3 (`wisp.local.engine.LocalEngine`): `start(conversation, model, mode)` and `resume(conversation, model, mode)` return a `Session`; `await send(session, text, emit, model=None)` runs one turn and calls `emit(event)` for each event; `model` may differ on every turn and the tier, tools and context budget follow it. `resume` rebuilds the history from `conversas/<id>.jsonl` (only `user` and `assistant` text lines); the engine has no session store of its own, and it does not write the transcript: the caller records the user and assistant lines (`record_turn` does it for the CLI, with `engine: "local"` and the model). `send` is a coroutine with a callback, not an async generator, so cancelling it (a stopped conversation) unwinds the MCP servers and withdraws any pending approval in the same task.
- Events are Claude's stream-json lines, so `ClaudeStreamDecoder` renders them unchanged: `system/init` (`session_id` is the conversation id, `apiKeySource` "none", plus `engine`, `tier`), `assistant` with `text`, `thinking` and `tool_use` items (ids `toolu_local_*`), `user` with `tool_result` items, `result` (`result`, `is_error`, `permission_denials`, plus `engine`, `model`, `stopped` and `steps`). The golden stream is `cli/tests/fixtures/contract/local-engine-events.jsonl`; a Swift test decodes it. One assistant event per model reply (Ollama is read streaming, the reply is emitted whole). Notes the guardrails add to a reply ("↳ ...") are an `assistant` text event and are also appended to `result`.
- Approvals are the engine's own, in `wisp.local.approver`: `LocalEngine(approver=...)` takes an `Approver` (`async ask(tool, arguments, tool_use_id)` returning `allow`, `deny` or `timeout`; the default is `DenyApprover`, so an engine built without one runs no gated tool). The loop asks for: the irreversible tools (`email_send` and `run_shell` are the built-in floor), the tier's `approve` list, and in `default` mode every tool that is not read-only (`READ_ONLY` in `guardrails.py`; an unknown MCP tool counts as a write). `email_send` has no exemption: the email tool no longer asks by itself (Claude gates it with its `ask` rule; here the loop does), so it is carded in every mode and tier, and the call only reaches the tool after `allow`. Nothing the model can write or call answers a card: there is no approvals folder or decision file. `TtyApprover` (`wisp local chat`, default `--approvals tty`) prints the tool and its JSON arguments and reads the answer from `/dev/tty`, never stdin, so piped input cannot answer; only `s`, `sim`, `y` or `yes` allows, anything else, EOF or no terminal denies, and 600 s without an answer is `timeout` (denied). `StdioApprover` (`--approvals stdio`, the host spawns the process) writes Claude's `control_request` line on the event stream (`{"type":"control_request","request_id":"req_<hex>","request":{"subtype":"can_use_tool","tool_name","display_name","input","description","permission_suggestions":[],"tool_use_id"}}`, so `PermissionRequest` and the bot's `pedir_permissao` render it unchanged) and waits for the matching `control_response` on stdin (`response.subtype` `success` with `response.behavior` `allow` allows; `deny`, an error subtype, a closed stdin or 600 s without an answer deny; lines for other request ids and non-JSON lines are ignored). With `stdio` the message must come in `--message TEXT` (`-` is refused), because stdin belongs to the host's answers. A denied or timed-out call is named in `permission_denials` and the model reads "o usuário negou a ação" or "ninguém aprovou a tempo". `permission_suggestions` is empty, so "Sempre permitir" never shows for local tools. Not verified: the app and the bot do not spawn the local engine yet, so the stdio shapes are pinned by tests against a scripted host and the Swift/bot decoders' tests, not by a real app or bot run, and the TTY path was tested with a pipe standing in for `/dev/tty`, not a real terminal. `WISP_TELEGRAM_THREAD` is passed to the tool servers from `--thread`.
- Guardrails (`guardrails.toml`, validated on load; an invalid file stops the turn with the file, section and value, and nothing runs): tiers `pequeno`, `medio`, `grande` with `max_steps` (model replies per turn, 0 = no cap; the tools of the last allowed reply still run, then the turn stops), `tools` (allowlist) and `approve`; `[irreversible] tools` can only add to the built-in floor `email_send` and `run_shell` (code, not config); `[loop] repeat_limit`: the Nth identical call (same tool, same arguments) in a turn is not run and stops the turn. ## core / Meetings

- Capture path: a source callback only copies samples into its `CaptureRing` (a preallocated single-producer single-consumer ring of 48 slots of 4096 frames, up to 4 channels, atomics only, no lock and no allocation; a full ring drops the chunk and counts an overrun). A 50 ms timer on one serial writer queue pops the rings, downmixes to mono, resamples to 48 kHz, mixes and writes. `MeetingRecorder` state is touched only on that queue.
- `StereoMixer`: L = mic, R = system, aligned by host time (`AudioTimeStamp.mHostTime` from the tap, `AVAudioTime.hostTime` from the engine, both converted by `HostClock`), not by arrival order. The origin is the earliest first chunk of the two sources: nothing is placed until both have delivered, or until one has more than `maxSkewFrames` (0.5 s) waiting, or on flush. A chunk that starts within `toleranceFrames` (25 ms) of where the lane ends is appended as contiguous, so timestamp jitter inserts nothing; further ahead it is preceded by silence, further behind its overlap is dropped, and anything before the already written position is dropped. Residual drift (the two clocks differ by some ppm) therefore builds up unnoticed up to 25 ms and is then corrected in one step by the gap or overlap rule; the tap's drift compensation is on as well. Past `maxSkewFrames` of difference the lagging lane is padded with silence so a source that goes quiet never stalls the file.
- `LinearResampler`: stateful across chunks (the result is the same however the input is cut); the same rate is a pass-through; a lane restarts its resampler when the rate of a slot changes (a device switch).
- File: during the call the audio goes to `audio.caf` (PCM 16-bit stereo 48 kHz), which a crash leaves readable; at stop it is encoded to `audio.m4a` and the CAF is deleted. If encoding fails the CAF stays, the status is `failed` and the result points at it. `RecordingRecovery.recover(root:)` runs at app launch: a folder whose `meta.json` says `recording` is encoded, the raw file removed and the status set to `interrompida` (audio ready but cut short; the ASR step must treat it like `transcribing`); an empty or unconvertible one becomes `failed` with the reason and keeps the raw file.
- `MeetingRecorder`: the folder name is the start time in the local zone, a second recording in the same second gets `-2`. Start order: support gate, folder, free-disk check, sink, mic, system; any failure removes the folder and stops what had started. Sources are stopped before the final flush and the rings are drained after that. Duration is frames written / 48000. `meta.json` ends as `transcribing` (nothing consumes it until the ASR step) or `failed`.
- Warnings (`warnings()`, shown in the pill as an amber dot and in the sidebar): a source that delivered no frames for 5 s ("o microfone parou" / "o áudio do Mac parou"; a source that never delivers is flagged 5 s after the start), an all-zero system channel for 10 s ("não estou ouvindo o áudio do Mac: libere em Ajustes do Sistema › Privacidade › Gravação de áudio"; shown once per recording, cleared when sound arrives; a Mac that is simply playing nothing for 10 s triggers it too), and ring overruns. `health()` is the fatal one: a write error or less than 200 MB free stops the recording.
- `CallAppCatalog.app(forBundleID:)`: exact id first, else the longest catalog id that is a dotted prefix (so `com.google.Chrome.helper` is Chrome). Browsers are `kind: .browser` since the id alone does not say it is a call.
- `MeetingCaptureSupport`: Core Audio process taps exist from macOS 14.2; below that the recorder refuses with a pt-BR message (the app's deployment target is 15, so it is a guard, not a path users hit).
- `recordingsPath` is read from the settings file only; its screen in Ajustes belongs to the Paths PR, which owns Ajustes > Caminhos.

## core / Meetings transcription

- ASR engine: FluidAudio 0.18.4 (Apache-2.0) running Parakeet TDT 0.6b v3 on the Neural Engine, the choice of the call-transcription spec. It stays in the app target; `WispCore` only knows the `SpeechRecognizer` protocol (`transcribe(samples16k, language) -> [RecognizedSpan]`), which is what the tests fake. FluidAudio's own batch API (`AsrManager.transcribe`) is used on short windows, not its streaming managers, so "live" is a window loop of ours. The model is `FluidInference/parakeet-tdt-0.6b-v3-coreml` (CC-BY-4.0), encoder `Encoder_v2` (int8, the build that avoids the token corruption of the palettized original), loaded with `AsrModels.loadLocal` from the Wisp folder.
- Channels: mic is `AudioChannel.mic` (speaker `eu`, shown "Você"), system is `.system` (`outros`, "Outros"); `falante-N` is reserved for the later diarization step and shows as is.
- `Decimator48To16`: 3:1 box average, stateful across chunks. The recorder hands 48 kHz mono per channel to an optional `onAudio` callback on the writer queue, before mixing, so the transcript never depends on the stereo alignment.
- `ChannelStreamer` (one per channel): a final window every `window - overlap` seconds (live: 5 s window, 1 s overlap, so a final every 4 s; final pass: 30 s window, 2 s overlap) plus, live only, a partial every 1.5 s over the audio since the last window start. A window whose RMS is under 0.003 is not sent to the recognizer (no hallucination on silence) but still closes the window, as a final job with no samples, so a stale partial is cleared. `flush()` sends the remaining tail unless it is under 0.6 s or already inside the last window's overlap.
- `TranscriptMerger`: one partial per channel, replaced by the next partial and dropped by any final of that channel. A final or partial that starts within 0.75 s of the channel's last final loses the leading words it repeats from the end of that final (case and punctuation ignored, up to 12 words); a fully repeated one is dropped. Finals are kept sorted by start. This is the only dedupe; nothing compares across channels.
- `LiveTranscriber`: pushes are synchronous (decimate, cut windows, enqueue under one lock), so order is the order of the audio; one worker task runs the recognizer. A pending partial of a channel is replaced by a newer one, finals are never dropped, so a slow Mac skips partials before it skips text. A recognizer error is reported once and the loop continues (the final pass redoes everything). `MeetingTranscriptStore` writes `transcript.live.json` after every final, so a crash keeps what was heard.
- Final pass (`MeetingTranscriber`): reads `audio.m4a` (or the raw `audio.caf`) in 1 s blocks, decimates each channel to 16 kHz (linear resampler when the file is not 48 kHz), runs the 30 s window config, then `TranscriptTidy.mergeAdjacent` joins same-speaker lines at most 1.5 s apart (under 320 characters) so the transcript reads as speech turns. A channel the meeting did not record (`sources`) is skipped. Result: `transcript.json` (spec shape), status `transcribed`; the live file is deleted.
- `MeetingPipeline.process`: for `transcribing` or `interrupted` (also a recovered recording) it transcribes, then writes the note, status `noted`. A recognizer failure sets `failed` with the reason and rethrows; "Tentar de novo" in the UI sets it back and reruns. An empty transcript stays `transcribed` with "nenhuma fala detectada" and no note. The note writer runs `wisp reuniao nota <folder>`; if it fails or writes nothing, the pipeline writes a raw note (the transcript under "Nota não gerada: <reason>"), status `noted`, `note_state: raw`, `failure` set, so there is never nothing; "Gerar nota de novo" retries only the note.
- `wisp reuniao nota <folder>` (cli): one turn with no tools, two attempts of 600 s. Backend choice: when the active engine is Claude (or anything but Codex) it is Claude. When it is Codex the note is NOT written by Codex (its shell can read any file on the Mac, so speech in a meeting could make it copy a secret into `nota.md` and then the brain): Claude is used if `claude --version` runs, otherwise the local engine if Ollama is running and the active model in `modelos.toml` is installed, otherwise the note is skipped and the raw note says "Nota não gerada: o motor ativo é o Codex… e o Claude e o modelo local também não estão disponíveis". The local path calls Ollama's chat API directly with `tools: []` (nothing but the prompt; no `wisp local chat`, no guardrail tools, no MCP server), and the test asserts the request's `tools` is empty and that nothing but `claude --version` is spawned. The prompt frames the transcript as untrusted data and as the only source of truth; "Você" is the microphone. Output: frontmatter + the model's title, Resumo, Decisões, Ações (owner and deadline per action) + the verbatim transcript with times and speakers. Written 0600 as `nota.md`; prints one JSON line (`nota`, `gerada`, `motivo`, `titulo`, `motor`, `pedido`). A per-meeting `flock` on `.nota.lock` makes a second run exit 3 (`ocupado`) instead of racing; the app then leaves the meeting waiting and does not retry it that session. A transcript over 150 000 characters keeps its first and last half and has `[... middle of the transcript omitted ...]` in between, announced in the prompt.
- Model files: manifest of 20 files pinned to HF revision `7dd20fe6…` (632 169 729 bytes, 0.6 GB): `Preprocessor`, `Encoder_v2`, `Decoder`, `JointDecisionv3` (`.mlmodelc`) and `parakeet_vocab.json`. Sizes and hashes come from the Hub's file API for that revision (LFS files: SHA-256; small git files: git blob SHA-1, verified as `sha1("blob <size>\0" + data)`). Download goes to `<wisp>/modelos/parakeet-tdt-0.6b-v3-coreml.partial/`, one file at a time to `.part`, checked for size and hash before it is kept; a retry keeps the files already verified; at the end the folder is renamed and `.wisp-verified` (the revision) is written. Refuses below size + 2 GB free (counting what the partial folder already holds). `isInstalled` checks the marker and every file's size. Cancel stops the transfer and leaves the partial folder for the next try.
- Brain export: `<brain>/meetings/YYYY-MM-DD-HHhMMm-<slug>.md` (a taken name gets `-2`), plus a line `- [[name]] — title` (at most 200 characters) in `meetings/meetings-index.md` only if that index already exists. It is the user's click, never automatic.
- Permissions card: the microphone state comes from `AVCaptureDevice`. macOS has no public query for the system-audio permission, so it is `unknown` until a recording: sound on the Mac channel marks it `granted`, the existing 10 s all-zero warning marks it `denied` (both remembered in UserDefaults and corrected by the next recording). The card appears only for a denied source the current choice uses. The Settings links are `Privacy_Microphone` and `Privacy_AudioCapture`.

The transcript sits between `BEGIN TRANSCRIPT <nonce>` and `END TRANSCRIPT <nonce>` lines (random nonce per run, removed from the text if it appears there), and the system prompt names the markers as data.
- System-audio permission: silence never becomes a stored "denied". While the current recording has been silent for 10 s, `SystemAudioWatch` makes the tab show a neutral grey hint ("Não estou ouvindo o Mac...") with the Settings button, not the yellow permission card; it clears when sound arrives and only "granted" is remembered.
- `MeetingPipeline.process` does nothing for a `noted` meeting whose `nota.md` exists; only `regenerateNote` rewrites it.
- The final pass has a pause gate checked before every recognizer call; the app holds it while a recording runs and it resumes by itself. The gate and the queue wait loop propagate cancellation (quitting the app cancels them). Live and final passes use two separate recognizers (two `AsrManager`s), never one shared. Stopping awaits the live worker (`stopAndWait`) before the final pass; a late result is dropped, and `transcript.live.json` is only read when there is no `transcript.json`.
- Live queue: a partial is dropped while a final of the same channel waits; finals are never dropped; with 3 or more finals waiting (about 12 s behind) the tab shows "Transcrição atrasada".
- Live times: `LiveAudioAligner` places each channel on one shared origin (the first chunk's host time), pads gaps over 25 ms with at most 2 s of silence (a longer gap is reported to the streamer, which flushes what it heard and skips ahead on the timeline without buffering zeros), drops overlap and trims audio before the origin, so both live channels share a clock. The file's own origin is the earliest first chunk of both sources, so a live time can differ from the file's by the start skew between the two sources.
- Model: every file's SHA-256 is computed after the download and stored in `.wisp-verified` (JSON); the app re-checks every file against the compiled manifest (`verify`: SHA-256 for the LFS files, git blob SHA-1 for the others; the marker only says an install finished, it never supplies expected values) before marking the model ready. Install is a rename of the staging folder with the old folder moved to `.backup` first and moved back if the rename fails. Manifest paths with `..`, `.`, empty parts, a leading `/` or a backslash are refused before any download.
- Brain export: `[[`, `]]`, `|`, CR and LF are removed from the title in the index line; a `meetings` folder or index that resolves outside the brain (symlink) is refused and nothing is written.
- Attribution: the CC-BY-4.0 notice (NVIDIA author, FluidInference conversion) is shown on the model download card and in Ajustes > Sobre.
- Cancellation: `WispNoteWriter` runs `wisp reuniao nota` through `CommandRunner` with a `CommandCancellation`; cancelling the Swift task (a cancelled queue, "Cancelar nota", app quit) sends SIGTERM to the command's whole process group (then SIGKILL after the runner's grace), which includes the engine child. A cancel before the process starts kills it as soon as it registers. "Gerar nota de novo" is a task the tab can cancel.
- Memory: the live and the final-pass recognizers are two `AsrManager`s (about 600 MB each). The final-pass one is unloaded when its queue is empty and, through `MeetingPauseGate`, the first time its pause gate sees a recording running; the live one is unloaded when the recording stops. Models load lazily again on the next use.
- FluidAudio is pinned by commit (`e0c6103…`, tag v0.18.4) and its Apache-2.0 license is in `app/Resources/ThirdParty/FluidAudio-LICENSE.txt`, opened by Ajustes > Sobre > Avisos de terceiros. The model manifest now also pins SHA-256 for the 8 files that the Hub only publishes a git SHA-1 for (the Hub's file API gives an LFS SHA-256 for the others): the 8 small files were fetched once to a scratch folder, checked against their git SHA-1 and hashed, and the scratch folder deleted. `verify` and the download check both hashes.
