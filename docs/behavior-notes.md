# Behavior notes

Developer notes: traps, invariants and external-system quirks, grouped by module.

## core / Blocks

- `TaskList`: the "feito" key is the exact line (without newline) plus its occurrence index, so two identical lines stay distinct. The occurrence is counted over every line, the same way `deleting` counts. When the removed line was the last one and had no newline, the line before it keeps its own newline. Splitting is on "\n" only (Foundation literal search, not `split`): Swift reads "\r\n" as one Character that never equals "\n", and rejoining with "\n" must give the same bytes.
- `CommandTemplate`: each value is passed as one single-quoted shell word (`it's` -> `'it'\''s'`), so a key with spaces or quotes cannot split or inject.
- `BlockCommand`: runs through `zsh -c` with the login shell's PATH (a GUI app inherits a minimal one); blocking, call off main. The shell leads its own process group so a timeout signals it and everything it started (SIGTERM, then SIGKILL shortly after; always reaped). The parent closes its copies of the child's pipe ends, or the readers never see EOF. Both pipes are drained while the process runs, so a large output cannot stall it; after exit it waits at most a second for readers (a background child may hold the pipe).
- `AlertList`: `nivel` is `red` or `yellow` (anything else reads as yellow); open time is `aberto_ts`, else `ts`; red first, then newest. Dates accept ISO 8601 with or without fractional seconds and `Z` or `-03:00` / `+0530` offsets.
- `AgendaList`: `allDay` events carry dates, not times; a `declined` response is excluded from now / next / count; all-day first, then by start.

## core / Agenda (native Calendar and Reminders)

- `AgendaService` runs over the `AgendaStore` protocol (`EventKitStore` in production, a fake in tests); `wisp-agenda` is only its `main`. Output is JSON on stdout; an error is one pt-BR line on stderr: exit 1 generic, 2 permission, 3 needs the user's confirmation (event with guests).
- Permission: denied, restricted and write-only read as "no access" (the message says "ler" for reads and "alterar" for create/edit/delete/complete; write-only says Wisp only has write access and needs full access) and are never asked again (the error names Ajustes do Sistema > Privacidade e Segurança); only `notDetermined` asks (the one system prompt), waiting at most 60 s: past that it exits 2 with "abra o Wisp no Mac e permita a agenda em Ajustes > Agenda". `calendarios` still lists the kind that was granted. `permissao` prints `{"eventos": state, "lembretes": state}` without asking; `permissao --pedir` asks for the undetermined ones. Ajustes > Agenda ("Agenda: permitir acesso") runs the embedded helper this way from the app process, so the prompt is attributed to Wisp; a helper started by the Telegram bot (launchd) may need that grant done once from the app first. Both Info.plists carry the usage strings and both signatures carry `com.apple.security.personal-information.calendars` (the helper target also sets `CODE_SIGN_ENTITLEMENTS`, so Debug and local builds have it). Not verified on a real prompt.
- Recurring events: `eventos` prints `"recorrente": true` and an occurrence id `<eventIdentifier>@<start ISO>`; the store finds that occurrence by searching one day around the start and matching the identifier and the start to the second, then uses `.thisEvent`. Edit or delete of a recurring event by its bare id is refused; `--serie` is explicit and uses `.futureEvents` (that occurrence and the next ones, "esta e as próximas"; never the past ones, so not the whole series). A bare id that ends in `@something` that is not a date-time (Google ids) stays whole.
- Edit and delete of an event with guests need `--confirmo` (exit 3 otherwise); it is a convention the agent must only pass after the user said yes, not enforcement. Edit also checks the final end against the final start (all-day events may be equal).
- Limits: `eventos` ranges are clamped to 92 days and cut at 200 items, and the output is `{"events": [...], "truncado": bool}`; `lembretes` without `--pendentes` returns pending ones plus those completed in the last 30 days (completed with no date are left out).
- Ranges: `--hoje` is today 00:00 to tomorrow 00:00 (local zone); `--semana` and the default are the next 7 days from today 00:00; a date-only `--ate` includes that whole day; no `--ate` means 7 days after `--de`. Output times are ISO 8601 with the local offset; an all-day event prints dates (`yyyy-MM-dd`) with an inclusive end, as EventKit stores it.
- Input times accept ISO with offset (`-03:00` or `-0300`), `yyyy-MM-ddTHH:mm[:ss]` or `yyyy-MM-dd HH:mm` (local zone) and `yyyy-MM-dd` (date only). An event whose start and end are both date-only is all-day; a reminder with a date-only `--quando` has a due date without time.
- Calendar and list names match case- and accent-insensitively; an unknown or ambiguous name errors with the options, a read-only calendar refuses writes.
- Event ids are EventKit's `eventIdentifier`: a recurring event keeps one id for the whole series, and edit and delete use `.thisEvent`, so they touch the occurrence EventKit resolves for that id. Reminder ids are `calendarItemIdentifier`.
- `wisp agenda` (Python) forwards its arguments untouched to the helper: `$WISP_AGENDA_BIN`, else `/Applications/Wisp.app/Contents/Helpers/wisp-agenda`, else `~/Applications/Wisp.app/...`. The runtime lives in `~/.local/share/wisp/runtime`, outside the app, so the app is found by those paths; the app sets `WISP_AGENDA_BIN` from `Bundle.main` in the agent's environment, so any install location works for it; if `WISP_AGENDA_BIN` is set but the file is missing, the command errors instead of trying the other paths. A helper killed by a signal returns exit 1 with a pt-BR line, never a negative code.

## core / Settings

- `HexColor`: `#RRGGBB` only; the 3-digit shorthand is rejected, not expanded.
- `WispSettings`: a custom theme picks accent, background and surface; the rest is derived. If the default text does not reach WCAG AA contrast (4.5) over a custom background, the side with better luminance is used. Saved tile order is always a permutation of `DashboardTileID.defaultOrder` (unknown ids and repeats dropped, missing appended). Files written before `dashboardOrder` existed decode to the default order. An unknown preset id (or "custom" without colors) falls back to the default lime.
- `WispSettings.settingsSection`: the Ajustes tab last opened; nil or an unknown id opens the first one (Aparência).
- `SettingsStore`, `ConversationStore`, `ClipboardStore`: written atomically; a corrupt file is moved to `<name>.bad` (a second corruption overwrites the older `.bad`) and defaults are used; the move is reported through the store's recovery note.

## app / Settings

- `IntegrationsPane`: one dropdown row per integration, one open at a time, all closed on arrival. `expandOnOpen` is a main-actor static set right before navigating to Ajustes > Integrações (the Música tab's "Abrir Ajustes") and cleared the first time the pane appears.
- `SpotifySettingsCard(embedded: true)`: inside an Integrações dropdown it has no title and no card of its own, since the host row already says "Spotify".
- `ToggleRow`: the whole row flips the switch (the switch itself ignores hits); an `accessory` before the switch keeps its own clicks.

## core / Memory, Routines, Profile

- `MemorySearch`: the search template fills `{query}` / `{root}` with shell-quoted values and must print `path<NUL>line:text` (grep/rg `--null -n`) or `path:line:text` (the first `:<digits>:` ends the path). BSD grep does not descend into a symlinked root (for example a vault linked into iCloud Drive), so commands get the symlink-resolved path. Obsidian names a vault after its folder; the `obsidian://open` URL percent-encodes every reserved character in both values, `/` included. Title matches sort first, else command order.
- `Routines`: `launchctl print` exits 113 ("Could not find service") for a label that is not loaded. Only the job's own top-level keys (one tab deep) are read; nested blocks such as the resource coalition repeat `state = active` and are ignored. Log tails read at most `maxBytes` from the end and drop a partial first line; "\r\n" is one Character in Swift, so it is a separator of its own.
- `Profile`: a `blocks` value of an unknown shape is ignored instead of failing the whole profile; a block with no command is a hidden tab.

## core / Spotify

- `SpotifyAuth`: PKCE verifier is 48 random bytes, base64url without padding (64 characters; RFC 7636 allows 43-128). The redirect is the loopback IP literal `127.0.0.1`: Spotify rejects `localhost` and allows plain HTTP only for loopback literals. A refresh response may omit `refresh_token`; then the previous one stays valid.
- `SpotifyModels`, `SpotifyRequests`: Feb 2026 API changes: a playlist's `tracks` became `items` (`tracks` kept as a deprecated fallback) and a playlist row's `track` became `item`; dev-mode `GET /search` allows at most 10 per type. An element that is `null` or undecodable decodes to nil so one bad item never drops a page. Episodes carry their own images instead of an album. Player 404 = no active device; player 403 with `PREMIUM_REQUIRED` (or a "premium" message) = not a Premium account. The play target is the active device, else this computer, else any controllable one.

## core / Memory graph

- `LinkGraph`: links resolve like Obsidian: by basename, case-insensitive, shortest path first; an unresolved link becomes a ghost node, except attachment extensions (never ghosts). Edges are undirected and de-duplicated, stored with `a < b`. Code fences and inline code are ignored when extracting links. The scan caches link targets by mtime and size; iCloud files not downloaded (`SF_DATALESS` flag, or legacy `.name.md.icloud`) are never read, since reading would block on a download. The base path goes through `realpath` so it matches the `/private/var/...` form the enumerator yields.
- `GraphLayout`: d3-force model with Barnes-Hut repulsion. Cooling is 300 steps from alpha 1; when most positions come from the cache it starts lower and settles in about 100. Seeding indexes each source once (O(N)); the layout on screen wins over the one on disk. Nodes without a seed start beside a seeded neighbour, else on a phyllotaxis spiral. A drag holds alpha at 0.3 (d3 `alphaTarget`); link strength is d3's `1 / min(degree)` times a multiplier; collision is one d3 forceCollide iteration, unscaled by alpha, on a grid of cells two max-radii wide. Panel values out of range clamp, missing ones default.

## core / Agent, Store, Telegram

- `AgentSession`: decoding under the lock keeps yields in stream order across handler invocations. Orphaned grandchildren can hold the pipes open, so the exit is emitted once the process is gone anyway.
- `ClaudeLocator`: the login-shell PATH is computed once per process.
- `ConversationReducer`: pure state machine over session events; when the session is gone, no queued turn can still produce a result.
- Permission prompts (confirmed against Claude Code 2.1.327 in a scratch folder, 18/11/2026): in `-p --input-format stream-json` a tool call that needs approval reaches the host only with `--permission-prompt-tool stdio`. Without it (`--permission-prompts` defaults to `host`, an `initialize` control request sent or not) the call is denied on the spot (`system/permission_denied`, `permission_decision.source: "config"`). No `initialize` is needed. The CLI writes `{"type":"control_request","request_id":R,"request":{"subtype":"can_use_tool","tool_name","display_name","input","description","permission_suggestions":[...],"blocked_path"?,"tool_use_id"}}` right after the assistant's `tool_use` and holds the call until the host writes one line on stdin: allow `{"type":"control_response","response":{"subtype":"success","request_id":R,"response":{"behavior":"allow","updatedInput":{...}}}}` (`updatedInput` may be left out in this version; Wisp echoes the input), "always" adds `"updatedPermissions":[suggestions]`, deny `{"behavior":"deny","message":M}`. Deny makes M the tool result (`is_error`, source `user_reject`) and Claude goes on; the tool still lands in the result's `permission_denials`, so the reducer drops the "libere em settings.json" hint for tools the user denied. Suggestions seen: `addRules` (`destination: "localSettings"`, i.e. `<cwd>/.claude/settings.local.json`; Bash `touch probe1 *`, WebFetch `domain:example.com`), `addDirectories` and `setMode acceptEdits` (both `session`). Sending all of them also switched the session to `acceptEdits` (a `system/status` line), so "Sempre permitir" sends only `addRules` with a non-session destination and shows only when there is one (Write offers none). `control_cancel_request` (drops a queued request) is handled but was not observed. Other `control_request` subtypes are ignored: Wisp registers no hooks or SDK MCP servers.
- Permission modes: `--permission-mode` accepts `default` (the help lists `manual`; init reports `default` for it), `auto`, `bypassPermissions`; the flag beats `permissions.defaultMode` in settings, and with no flag the CLI uses that setting. `auto` ran in `-p` on the owner's account (init `permissionMode: "auto"`, calls accepted with `reason_type: "mode"` or `"classifier"`; the classifier even accepted `rm -rf` of a sibling scratch folder). If the CLI reports another mode at init after Wisp asked for `auto`, the conversation says so and Ajustes shows Automático disabled for the rest of the run (how an account without `auto` behaves was not observed). `bypassPermissions` still runs `PreToolUse` hooks (a scratch hook exiting 2 blocked the call, `source: "hook"`) and `permissions.deny` rules (`reason_type: "rule"`), so the harness deny list and the secrets guard hold in every mode.
- Explicit `ask` rules in bypass (measured 20/11/2026, Claude Code 2.1.329): `claude -p --model haiku --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --permission-mode bypassPermissions --settings '{"permissions":{"ask":["Bash(*aprender add*)"]}}'`, asked to run `./fakewisp aprender add "regra teste"`: init reported `permissionMode: bypassPermissions`, the CLI emitted a `control_request` `can_use_tool` for that Bash command, and the command did not run while the request stayed unanswered. So an `ask` rule with a leading `*` matches and prompts even in bypass. Without a prompt host (`-p` without `--permission-prompt-tool stdio`, as in the Telegram bot today) such a call is refused.
- `PermissionSetting`: Wisp's own setting (only set while the profile is a link) wins, then the profile's `agent.permissionMode`, then `permissions.defaultMode` from `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR`), shown as "Definido no Claude" and never written. Unknown values count as unset. The profile is rewritten with sorted keys; a missing profile gets the persona/agent defaults the app needs to decode it.
- `TranscriptReader`: incremental, a line is read only once its newline lands. The project folder name is the cwd with every character outside `[A-Za-z0-9]` replaced by "-", one per Unicode scalar (same as the bot's `sessao.slug`). The CLI writes one line per content block. Injected prompts (slash commands, local command output, reminders), interrupt placeholders and the bot's own follow-up turn are not part of the conversation; when the session moved machine the bot wraps the user's message in context and the message follows a marker.
- `TranscriptFollower`: state is touched on its queue only. A missing file is a real state (a topic before its first turn): reported once, empty. On change the next poll reopens whatever sits at the path; a replaced file is read again from the start with a fresh parser. The descriptor outlives the dispatch source, never the reverse.
- `TelegramHTML`: `&amp;` is unescaped last so `&amp;lt;` becomes `&lt;`, not `<`. It also reads `br`, `blockquote` (`> `) and `strong`/`em`; Markdown code the model wrote (a fence or an inline span) is left as typed, so a `<b>` shown as code stays a literal. It runs once, when text enters the app: `ConversationReducer` (live `text` and `result`) and `TranscriptParser` (history, follower, previews), never again at render.
- `AgentInstructions`: the prompt (`--append-system-prompt`, `ClaudeCommand`) and env the app gives its `claude`. An app turn ALWAYS gets `appFiles` ("here" is the app: a file is a `[name](file:///abs/path)` Markdown link that opens on click; tested against `cli/tests/fixtures/contract/app-files-instruction.txt`), whatever else the conversation is. In a topic with a known wisp binary (`TelegramBlock.binary`, the unquoted `<bin>` of the `list` template; nil for a custom one) it appends `appSharedNote` (files linked here are sent to the topic automatically; only on an explicit ask for Telegram/the phone, `"$WISP_BIN" topic enviar --thread="$WISP_TOPIC_THREAD" FILE`) and sets `WISP_BIN` and `WISP_TOPIC_THREAD`. The bot's own turns get `telegramFiles` (= `TELEGRAM_FILES`, tested against `telegram-files-instruction.txt`): enviar to the topic. Both texts forbid calling the Telegram API directly and reading the bot token. After an app turn on a shared conversation, `FileLinks.absolutePaths` collects the `file://` links of the final assistant text (existing, readable, regular files, at most 10 and 50 MB each, outside the bot's deny-list folders, deduplicated) and the mirror passes them, plus the user's attachments, as `arquivos` of `telegram.post`, so the phone gets the file too. `TurnRestartPolicy` restarts a warm process whose topic differs from the conversation's current one (`contextChanged`), so a conversation unshared from Telegram stops carrying the bot's env.
- `TelegramTopics`: one conversation = one Claude session; Mac only. The bot runs a topic's turns and the app runs the app's, each under the flock of `~/.local/state/wisp/locks/<session_id>.lock`, so two turns of one session never overlap. A section's conversation is the one whose `sessionId` equals the topic's `sessionId`; the app shows "Respondendo pelo Telegram…" while the lock is held elsewhere. Wisp reads the transcript and talks through the profile's `blocks.telegram` commands: `status`, `list`, `share`, `post`, `close` and optional `attachments`. A partial `blocks.telegram` counts as no Telegram. `topics == nil` (never read) keeps every conversation in Wisp. `reading` comes from the status `reader` and is always this Mac.
- `ClaudeCommand`: `--permission-prompt-tool stdio` sends every prompt to the host as a `can_use_tool` control request; without it a prompt in `-p` mode is denied on the spot. A variadic flag goes before another flag so that flag ends its list.
- `FileOpenPolicy`: a click on a `file://` link opens only known document types in the default app; everything that could run or install (programs, scripts, archives, installers, launchers, bundles, shortcuts, macro files, executables on disk, unknown types) is revealed in Finder instead. The decision uses the symlink-resolved path.
- `FileLinks` / `SentFiles`: the files a reply hands over are the `topic enviar` calls the agent made plus the reply's `file://` links, deduplicated by resolved path (a symlink, `..` or `~` spelling of one file is one file) and capped at `FileLinks.maxFiles`. The shell expands `~/` and `$HOME/` before `wisp` sees the path, so the parser mirrors that. Anything the bot would refuse (its denied folders, unreadable or over-limit files) is skipped; APFS ignores case, so `~/.SSH` is `~/.ssh` and the comparison is case-insensitive and by file identity where the path exists.
- `PhoneHandoff`: the message the topic gets on "Continuar no celular" quotes the last reply the user can read (the one before the streaming one while a turn runs), cut at a word with an unclosed code fence closed. A pending approval can only be answered on the Mac: the bot cannot reach the process that holds it.
- `RuntimeLifecycle`: idle runtimes with a live process beyond the `keepWarm` most recent, or unused for `idleTimeout`, lose their process (state stays, the next message resumes); the conversation on screen and any busy runtime are never returned, and busy ones do not count toward the cap. A runtime with nothing left to keep is dropped and rebuilt from the transcript. In the sidebar an approval waiting or an unseen reply (attention) outranks a running turn.
- `ConversationTitle`: the title is the first message cut at a word boundary until one `claude -p` call (cheapest model, no session file, no tool, hook, skill or MCP server) writes a real one; a failure or timeout keeps the cut, and a conversation reopened from a record never asks for one.

## core / Usage, System, Media, Clipboard, Shell

- `UsageAggregator`: only files modified inside the window are opened, streamed line by line; each `message.id` counts once; a cheap byte check skips lines without usage. Cache reads are reported apart from the turn's spend. `UsageIndex` keeps the parsed lines of each transcript between reads (a week is hundreds of MB; reading it all cost about 2 CPU-seconds each time Home opened). Transcripts are append-only JSONL: a file that grew is read from the byte just past the last newline read; one that shrank, is new, or kept its size with a different modification date is read whole (a rewrite to a longer file is indistinguishable from an append and is not detected). A last line with no newline yet is counted but read again next time. One lock guards the index; its only caller is the detached task of `UsageModel`.
- `PlanLimits`: Wisp never reads the OAuth token nor calls the usage API; limits come from the statusline's `rate-limits.json` or the CLI's `rate_limit_event`, newest wins. A window whose reset time passed is stale.
- `UsageFormat`, `SystemFormat`: a value that rounds up to 1000 carries into the next unit ("999,96 GB" -> next unit, not "1000 GB"). Disk and network use decimal units (Finder), memory binary (Activity Monitor).
- `CPUUsage`, `NetworkRate`: counters are 32-bit and wrap; deltas are taken modulo 2^32. Nil when the CPU count changed or no time elapsed.
- `TemperatureSummary`: `PMU* tdie*` are SoC die sensors (Apple does not say which die is CPU or GPU), `NAND*` the SSD, `gas gauge battery` the battery; implausible values (`tdev` sensors report about -22 C idle) are dropped.
- `ProcessTable`: `ps` is setuid and sees every user's processes, `proc_pidinfo` only ours; `%cpu` may be above 100 and may use a comma decimal; `comm` may contain spaces.
- `VolumeUsage`: `available` is `volumeAvailableCapacityForImportantUsage` (Finder, purgeable counted as free); `availableRaw` is `volumeAvailableCapacity`.
- `MemoryBreakdown`: App = anonymous minus purgeable; Used = App + Wired + Compressed; Cached = file-backed + purgeable. Pressure level values are the kernel's: 1 normal, 2 warning, 4 critical.
- `NowPlayingParser`: fields are joined by U+001F; AppleScript writes reals with the locale's decimal separator ("12,5" in pt-BR).
- `ClipboardHistory`: items carrying an nspasteboard.org concealed / transient marker (including older markers some apps still write) are never stored; copying the same content again moves the entry up keeping its pin; pinned items are never evicted; big text copies are not recorded.
- `NotchGeometry`: the band hugging the notch never changes between rest and active; active only adds a strip below it.

## app

- `NowPlayingService`: every script is wrapped in `is running`, so a player that quit between the check and the script is never relaunched by `tell`. `AEDeterminePermissionToAutomateTarget` blocks (with `ask` it waits on the system prompt): it runs on its own queue, never main, and a prompting request has its own queue so an unanswered prompt does not hold back the other player's checks. No query at launch, so the Automation prompt never appears out of context; only a player that already granted Automation is queried; the prompt comes from "Permitir controle". A grant is cached (the 1 s ticker must not hit tccd); a revoke surfaces as -1743. The wildcard permission check does not prompt, a real harmless Apple Event does. Local files and ads have no artwork URL; that must not hide the track.
- `ShellController`: window-server routing ignores `hitTest`, so outside the pill the window stops taking events outright; the global monitor keeps firing and flips it back when the cursor enters. Hover-open never steals the keyboard. Leaving `.panel`, a window that stays key keeps eating keystrokes, so it is cycled out of the window list and focus returns to the previous app only if the user did not switch apps meanwhile. Frames jump (not slide) across displays. `CGRect.contains` excludes the max edges; the cursor can sit exactly on the top edge.
- `WispAvatar`: the still figure (Reduzir movimento, or `animates` false) and the animated one draw the same parts; only the motion lives in Core Animation, so the render server runs it and the app does no per-frame work (the 30 fps `TimelineView` it replaced re-laid out the whole panel every frame). Layers are fixed; a size, accent or backing-scale change redraws their baked images and restarts the animations. Layer geometry is y-up. Animations run at 10-30 fps (30 fps is plenty for a 1.5 pt float). Blinks: three slots of 5.5 s per loop, each blink at a pseudo-random spot, so gaps vary from 4 to 7 s; the eyes close to 12 % for 0.16 s.
- `-WispOpenPanel <tab>` (a `PanelTab` raw value, e.g. `myMac`) opens the panel on that tab and keeps it open through outside clicks, to measure each tab without a mouse; `-WispNoKeychain` skips every Spotify keychain read and write (Spotify shows as not connected), so a freshly signed measurement build does not raise the keychain prompt on every launch. Both exist only in Debug and in builds compiled with `WISP_PERF`.
- `SpotifyKeychain.adoptLegacyItem`: copies the session saved under the previous bundle id's service, once, when the new service has none; the old item stays where it is.
- `PillView`: an always-on 30 fps timeline in the resting pill cost 6-12% CPU, so it animates only while busy. The pill sits in a top-aligned centered overlay so its fixed size never feeds back into the hosting view's window size.
- `ComposerView`: corner radius is half the one-line height; `.continuous` at that radius left a half-filled 1pt column at the leading edge. The AppKit layout callback is deferred because it may run inside a SwiftUI update.
- `SettingsView`: the color panel must float above the notch panel or it opens hidden behind it.
- `SidebarView`: the Cmd-N shortcut button uses `.opacity(0)`; `.hidden()` would drop the shortcut.
- `AppSettings`: writes go through one queue (ordered); a color picker drag is debounced; flush on terminate so a change inside the window is not lost.
- `TelegramModel`: a failed list read keeps the last list (a missing topic would hand its session to local `claude`); a topic closed from Wisp is hidden at once, since its note may say active until the next brain sync. There is no claim step: sharing a conversation runs `share` (a topic on the same session, with a recap), and after each app turn on a shared conversation the app runs `telegram.post` so the topic mirrors the user's message and the reply (`wisp topic postar`, no Claude run).
- `TabModels`, `DashboardModels`, `MemoryModel`, `RoutinesModel`, `TelegramModel`: live for the process (the panel view is rebuilt on every open) and never act as source: every read goes back to the profile's file or command, the newest read wins, and a forced read during a running one runs again after it (the running read may predate an action). The agenda command hits the network, so non-forced refreshes within `maxAge` keep the last result.
- `MessageRow` (assistant text): links open only for `http(s)` and `file://` absolute local paths; a clicked file opens in its default app, a `.app` or executable is revealed in Finder instead of run, a missing file does nothing.
- `ConversationViewModel`: every turn, from the app or the bot, runs under the flock of the session (`SessionLock`); a conversation linked to a topic is still the app's to run. The app takes the lock per turn and keeps a lease while turns are queued, released when the last result lands (or the session is discarded). Before a turn the warm `claude` process is restarted for a fresh `--resume` (so what the bot said is in the context) when the session is shared in Telegram, the lock was contended, or its file changed after the app's last turn; never while a turn is in flight (`TurnRestartPolicy`), and the restart keeps pending turns, mirror users and the lease (`ConversationReducer.processRestarted`). Opening or starting a conversation resets the last-turn stamp. Session starts are serialized (one start at a time, the next waits for the stop) so two children never share one transcript; a start in flight notices a new generation and stops its own child. The pill reacts only to a result or phase change; `result` is the sole path that shows a reply in the pill.

[ ] { }` in the arguments. `ask` for every other command that names `agenda`/`wisp-agenda`/`WISP_AGENDA_BIN` as a word (every create/edit/delete/complete, `./wisp`, `/tmp/x/wisp`, `mywisp`, `/tmp/wisp-agenda`, a bare `wisp agenda`, chained or computed commands, a bare `agenda`), and for a command that references `wisp`/`WISP_BIN`/`WISP_AGENDA_BIN` followed by a word with `$`, quotes, glob, braces or a backslash, or together with `eval` (`wisp ag""enda`, `a=ag; wisp ${a}enda`, `$WISP_BIN a* apagar-evento`); nothing for the rest (`topic enviar` keeps its normal flow). `permissions.ask` rules in `harness/settings.json` and in the app's and bot's guard settings (`guard-settings.json` fixture) cover the mutating subcommands in the forms the agent is told to use (`"$WISP_BIN" agenda X`, `$WISP_BIN agenda X`, `wisp agenda X`, `"$WISP_AGENDA_BIN" X`); per the Claude Code docs an `ask` rule prompts even in `bypassPermissions`, while a hook `ask` under bypass is not documented, so the rules are the part that holds there. `harness_merge` appends missing `ask` rules like `allow`/`deny`. A hook that cannot read its input exits 2 (the turn is refused).
- Guard hooks (`wisp hook guard-*`, `guard_destructive`): best-effort, not a sandbox. - `session_lock` (bot): the blocking acquire runs in a thread; when the awaiting task is cancelled the thread still finishes, so a done-callback gives the lock back if it was won. The wait notice is cosmetic and never blocks the turn.
- Bot `_sh_err` (hosting): the child starts in its own session and a timeout kills its whole process group, like `sessao`/`topicos`.
- Send deny-list: `bot.py` (`NEGADOS_NOMES`, `NEGADOS_GLOBS`, `NEGADOS_PASTAS`) and `FileLinks.swift` (`denyNames`, `denyGlobs`, `denyDirs`) each hardcode the same lists; `cli/tests/fixtures/contract/send-denylist.json` is a drift test that fails if they differ, so change the three together. Besides names and folders, both sides read the first 4096 bytes of a file and refuse it if they contain `PRIVATE KEY-----` (or if the read fails); the marker and limit are in the fixture too. `.key` is not a denied name, so Keynote decks (zips) are sent.
- `hosting` pair rules (`hosting.py`): Telegram accepts ONE `getUpdates` per token, so two readers trade 409. Each bot is `active` (reads) or `standby` (only watches the other host). The claim `{host, ts}` lives only on the PC (`CLAIM`, survives reboot); nothing in the Wisp writes it any more, the PC loop rewrites it (`trocar_claim`, only over the claim it read) and copies it into its own `STATE` every beat, the Mac reads it on its normal check. PC with claim "pc" (or none) starts in `grace` for up to `GRACE_S`, then reads; the Mac seeing the grace stops reading and writes `peer-yielded` on the PC, which activates at once; Mac off or asleep = the PC waits the whole grace. PC with claim "mac" stays standby; if it was reading it yields only with no turn running and after pushing the notes, then stops the updater, lets the already-read updates become handlers and checks again (work arrived = reconnect and keep reading). Each Mac check writes `MAC_VISTO` on the PC (mtime = PC clock): no check for `MAC_FRESCO_S` (counted from PC boot) means the Mac slept, the claim returns to the PC and it reads without grace; Mac checking but not reading for `MAC_ESPERA_S` returns the claim through the grace; Mac in the post-409 block: the PC never yields to it, and if it already did the claim returns at once. `CLAIM_PENDENTE` (Mac only) holds a Mac claim that did not reach the PC; the loop delivers it on the first check that reaches the PC, dated from when it was asked, never over a newer PC claim; nothing in the Wisp creates that file today. The Mac reads at once on claim "mac"; otherwise only when the PC is not active/grace for `MISSES` checks in a row, or on the first check if Tailscale says the PC node is offline. An unreadable PC state (ssh/parse failed) never activates the Mac; only a valid "no bot" reading counts as a miss. Exception: ssh to Linux failing with "Host is down" / "No route to host" (kernel ARP unanswered) plus Windows ssh also mute, with the Mac on the PC's /24, is a valid "PC off" reading; timeout, refusal and auth stay unreadable. A 409 on the Mac drops the reading and blocks reactivation. All traffic goes through ssh Mac->PC: the tailnet ACL blocks the direct port (measured 30/09) and the Mac has no sshd; the PC never needs to reach the Mac. The PC clock stamps its own state (read with the PC's `date +%s`), so a skewed clock does not count. `solo` has one host: `rodar` activates the reading and only publishes the beat, no ssh.
- `hosting` vigia and probes: the Mac keeps a long ssh to the PC that prints one state line per second and, when the connection drops, its stdout closes and the next `echo` dies of SIGPIPE, so no orphan loop is left on the PC; a missing file is the line `{}`. A vigia "off" only wakes the Mac loop, which then does a real reading newer than it; only two mute probes after the PC closed the session skip that reading. The vigia never takes the Mac loop down. While releasing, the Mac never publishes standby until its running turn ends (the PC would read a forked session). The push has its own ceiling (process group killed); the outer timeout is only a safety net, and the handover never holds the yield.
- `sessao` (Mac <-> PC): the jsonl lives in `~/.claude/projects/<slug>/<session_id>.jsonl` with the slug being the absolute cwd with every non-alphanumeric replaced by "-"; copying it to the slug of the cwd where it resumes is enough for `claude --resume <id>` to recover the whole context, even when the `cwd` fields inside point to a path that does not exist here (verified 14/10). The Mac always starts (the PC cannot reach it) and the copy goes only over ssh: a session may hold secrets, so never through git or the brain. The remote shell on Windows is cmd.exe, which eats binary, so the file travels as base64 in a stream (never whole in memory; 57-byte multiples give 76-char lines with no padding in the middle) and integrity is checked by sha256. The PC does not pull, it asks: it leaves `<state_dir>/sessao-pedidos/<id>.json` and the Mac bot, which looks at the PC every hosting tick (30 s idle; 20 s missed the window), pushes the jsonl. A copy written in the last 2 minutes may have a live claude in it, so it is never replaced or deleted. The topic note decides the session: the host that takes over resumes the SAME one. A Mac turn in flight at the yield is marked on the PC (entries older than the expiry are junk from a Mac that died mid-turn; 60 s of clock slack); mirror candidates come from the PC's own `topics.json`, not the notes (which arrive up to 5 min late).
- `wisp arquivos` / `wisp mac` (`arquivos.py`, `mac.py`): every outside call (`mdfind`, `osascript`, `screencapture`, `pmset`, `open`, `/usr/bin/trash`) goes through the injected `Runner`, so tests never touch the Mac; osascript gets user text only after `--`, never inside the script. `buscar` reuses the send deny-list from `wisp_bot.bot` (`_negados`, `_fica_em_negado`), so there is still one list (and its fixture); it also drops `~/Library` and any hidden path component, and falls back to a bounded name walk (depth 6, 50000 entries) when `mdfind` fails or yields nothing usable. `organizar` looks only at the top level of a folder inside the home (never the home itself, `~/Library`, or a folder holding a project marker such as `.git`, `package.json`, `*.xcodeproj`), skips hidden files, symlinks and deny-listed files, and refuses a group folder that is a symlink, a regular file or resolves outside the organized folder (a warning in the plan, a failure at apply time). Names are free at plan time and again at apply time (`nome 2.ext`); the move itself is `renamex_np(RENAME_EXCL)` on macOS (link+unlink elsewhere), so it can never replace a file, and a dangling symlink counts as occupied. The journal `desfazer-<ts>.json` is one JSON object per line (header `{"version": 2, "pasta"}`, then `{"criada"}` / `{"de","para"}` lines), created before the first move and appended with fsync after each, so a crash or a failed move leaves a journal that undoes exactly what moved; a run that moves nothing leaves none, and two runs in the same second get `-2`. `desfazer` reads the whole journal first (a damaged one is refused without touching anything), restores in reverse with the same no-overwrite move, lists the files it could not restore, removes the folders the run created if empty and renames the journal to `desfeito-<ts>.json`. Trash moves are not in the journal (the Trash is the undo). `mac abrir` ports `FileOpenPolicy` by extension (no UTType in Python): folders, executables, files without extension, the app's reveal list and every extension not on the short safe-to-open list get `open -R` and the reply says it only showed the file; `open -a` is used only for an `.app` found by name in `/Applications`, `/System/Applications` (and their `Utilities`) or `~/Applications`. `mac print` writes to `~/.local/state/wisp/capturas/` (files older than a day are deleted on each print), not the Desktop; `--janela` waits for the user to click a window (`screencapture -w`, 60 s), so the instruction forbids it from Telegram. `mac nao-perturbe` only reads `~/Library/DoNotDisturb/DB/Assertions.json`, which macOS lets only an app with Full Disk Access read; without it the command says so (checked on macOS 27: "Operation not permitted"), and it never toggles Focus (private APIs). Permission denials are recognised from osascript's "not authorized" / -1743 text; a denied Screen Recording shows up as no output file. The app resolves `WISP_BIN` with `EngineGuards.wispBinary` (Telegram block, else the runtime or `~/.local/bin/wisp`), so the agent gets it without Telegram.

## Self-learning

- Store: `<brain>/wisp/aprendizados.md`, a short heading and one line per lesson, `- <rule> · <YYYY-MM-DD> · <origin>`; only lines starting with `- ` count. Lessons are deduped by their rule folded to lowercase, no accents or punctuation (the first stays); past 40 the oldest are dropped (`wisp aprender add` prints a stderr line naming each). A rule with a token-like secret is refused; the rule is cut at 240 characters and the ` · ` separator inside it becomes ` - `.
- Capture: `wisp aprender add "<rule>" [--origem <text>]` (`já sabia` for a duplicate); the agent is told to call it by the hook text itself, with the absolute path of the running `wisp`, so no per-surface prompt changes. The `ask` permission rules (`Bash(*aprender add*)`, `confirmar`, `descartar`) in `harness/settings.json` and in the app's and bot's `--settings` make the engine prompt the user before any of the three runs; per the Claude Code docs an `ask` rule prompts even in bypassPermissions mode and wins over a user's own `allow`. `wisp setup` also removes the legacy `Bash(~/.local/bin/wisp aprender add:*)` auto-allow older installs carry (`REVOKED_ALLOW`). `wisp hook guard-lessons` (`PreToolUse`, same three settings, never in the harvest's) denies (exit 2) Write/Edit/MultiEdit/NotebookEdit on the active and pending lessons files and Bash commands that name `aprendizados` next to a write operator (`>`, `tee`, `sed -i`, `mv`, `cp`, `python -c`...); best-effort, a shell can always find another way. The brain harvest prompt has a step for the same lines (corrections and preferences only, facts stay in notes), but it writes them to `<brain>/wisp/aprendizados-pendentes.md`; right after the model child exits OK, `quarantine` puts the active file back exactly as it was before the harvest (the model can only add, an edited or removed active line is restored) and moves anything it left there into the pending file. The harvest runs under the scope guard and `wisp/` is inside the brain.
- Confirm: harvested rules wait in the pending file and the agent never sees them until the user runs `wisp aprender confirmar <n>` (or the app's Brain settings); `descartar <n>` drops one. Python and Swift both write the active file first and only then remove the pending line (a failed write loses nothing) and skip a rule already active (same folding as the dedupe).
- Use: `wisp hook aprendizados` (`SessionStart`, in the app's and bot's `--settings` and in `harness/settings.json`) prints the active rules (without date/origin) framed as preferences the user taught the agent, plus the `aprender add` instruction. No brain configured or any error: prints nothing, exit 0. Lessons saved during a conversation reach the agent from the next session start (a new conversation, or a resume), not the one that is running. The once-per-session marker (`aprendizados-sessoes/<session_id>`) stores a hash of the active rules, so a resumed session gets the text again only when the active set changed (for example after a confirm), never for pending ones. A session started under both `harness/settings.json` and `--settings` may receive the text twice.
- Undo: `wisp aprender listar` / `wisp aprender remover <n>`; the app's "O que o Wisp aprendeu" removes by line text (not by number), so a concurrent write never removes the wrong rule.

## Recall and brain harvest

- Recall (`wisp hook recall`): runs on every user message and never fails the turn (any error prints nothing). A given note is offered once per session, so a long chat does not repeat itself. The injected header frames the snippets as reference data from the user's notes, not instructions; only regular files are read (a FIFO is skipped) and at most 64 KiB of each. `WISP_RECALL_OFF=1` makes it print nothing (the harvest child sets it).
- Harvest (`wisp brain colher`): a conversation is eligible after 30 min without messages and with at least 3 user messages since the last harvest. A ledger (`colhidos.json` in the state dir) keeps the transcript offset already summarized per session, so a later harvest reads only what is new. Sessions in use or whose Telegram topic is closed are skipped. The model child runs with `WISP_BRAIN_SCOPE` set to the brain root and a second PreToolUse hook, `wisp hook guard-brain-scope` (only in the harvest's own settings), which denies Read/Write/Edit/MultiEdit/NotebookEdit/Glob/Grep on any path (`file_path`, `notebook_path`, `path`, or the cwd when Glob/Grep have none; symlinks resolved) outside the brain, and Glob patterns that are absolute or climb out with `..`. Without the env var the guard allows; any error in it blocks.
- One run at a time machine-wide (global lock); `--if-due` skips when the last run was under 10 min ago, so the app and the bot can both call every 10 min without doubling work. Conversation text is never logged: callers log only counts of harvested and skipped.
- The switch is `brain_learn` in `wisp.json` (default true, Settings > Geral > Brain). Off means the command reports one skipped entry and does nothing.
- App side: `BrainColherScheduler` ticks at launch +2 min then every 10 min and never overlaps ticks (each awaits the previous); the CLI run lives off the cooperative pool since it can last minutes. The app reads only the two list lengths of the `--json` report, never the conversation names. `WispConfigFile` edits single keys of `wisp.json` and leaves the rest (the CLI owns the schema), refusing a symlink; choosing the brain folder also moves `blocks.memory.root` of `profile.json` (and `blocks.tasks.file` when it still pointed at the old `pendencias.md`), and writes nothing when the profile is missing, a symlink or not a regular file.

The app shows its normal approval card ("Sempre permitir" is hidden for this tool: `PermissionRequest` drops the `addRules` suggestions for `EngineGuards.askTools`; an `ask` rule would beat the saved allow anyway). The Telegram bot runs claude with `--input-format stream-json --permission-prompt-tool stdio`, sends the user message as a `user` line, answers each `can_use_tool` with a card (Permitir/Negar, only the configured owner; 600 s without an answer denies; a `control_cancel_request` or the end of the turn closes the card) and writes the `control_response` line itself; a turn without a handler (or a handler that raises) denies. A request too long for a Telegram card (4000 characters after HTML escaping) gets no Permitir button and is denied at once with "aprove pelo app" (the bot's claude process is not the app's, so the app cannot answer it: the model is told to ask the user to do it in the app). Not verified at runtime: a real Telegram card (the bot code is tested against a fake `claude` and a fake Telegram, not a live bot), the app card for `email_send` (Swift tested, app built but not driven), and the turn timeout (900 s default) running while a card waits.

It is a deterrent, not a sandbox: an encoded or downloaded script, another mail client (`sendmail`, `curl` over SMTP) or a script written in a way the patterns do not see still gets through. - `wisp harness sync` never follows a symlink inside `~/Wisp/skills`, so a link there cannot copy files from elsewhere into `~/.claude`.

## Conversation transcript

- Format (v1, `cli/tests/fixtures/contract/conversation-transcript.jsonl`): one JSON object per line in `<wisp_dir>/conversas/<conversation>.jsonl`, keys sorted, no spaces, UTF-8 unescaped, timestamps UTC with milliseconds. Kinds: `session` (`session`, `engine`, `reason` new or rebuilt: links an engine session id to the conversation), `user` (`surface` app or telegram, `text`) and `assistant` (adds `engine` and `model`, the model the CLI reported in its init event). Only the typed message and the final reply text are stored: never tool calls, tool output, file contents or the bot token (the bot replaces its own token with `[redacted]`). The Swift app (`TranscriptStore`) and the Python bot (`wisp_bot.transcript`) both write it, test each other's bytes through the fixture, and take `flock(LOCK_EX)` on the file for each append, so a line is never interleaved; a last line left half-written by a crash is closed with a newline before the next append. Files are `0600`.
- Identity: the conversation of the app and of a Telegram topic is already one thing through the Claude session id (`TelegramTopics.topic(forSession:)`, `compartilhar`). The transcript file is named after the first id the conversation had: the session id for a conversation that starts on Telegram, the app's conversation UUID (lowercase) for one that starts in the app, because the session id does not exist until Claude answers. Every later session id is linked by a `session` line, and both sides find the file by name first, then by scanning for that line. A reset (the Geral every 24 h) gets a new session id nobody linked, so it starts a new file on purpose.
- Rebuild: the engine session is a cache. The bot treats `claude` exiting with "No conversation found with session ID" as a lost session (`Result.resume_failed`, stderr or the result's `errors`); it also primes when it would start a fresh session for a conversation that already has history. The app does not guess from the session file's location (Claude may keep it under `$CLAUDE_CONFIG_DIR`): it always tries `--resume` and reacts to that same error on the running process, re-sending the prompts that were in flight. A conversation counts as having history only when the transcript holds at least one assistant reply, so a first turn that failed is never reported as a lost session. A rebuild starts a new session (new id, linked in the transcript, turns and cost of the topic kept) and prepends to the prompt a memory block: the last 6 messages up to 3000 characters each, older ones up to 400, 24000 characters in all, oldest dropped first; no model call. Without any transcript there is nothing to rebuild and the error shows as before.
- Writes fail open: the error is logged, the answer is delivered, and one notice per app run (app) or per bot run (Telegram) says the folder could not be written.
- A conversation whose session was rebuilt on one side now has a new session id there; the other surface still points to the old id. Plan 3 did not move the app-Telegram link to conversation ids (see "Engine interface", what is left).

## Engine interface

- One shape on both sides, small on purpose; the local engine (plan 4) plugs into the same one. **Swift** (`core/Sources/WispCore/Engine/EngineSession.swift`): `EngineSession` has `kind`, `events` (`AsyncStream<SessionEvent>`), `start()`, `send(_:)`, `respond(to:_:)`, `stop()`, `processIdentifier` and `routesApprovals`. "Resume" is the `resume` value of `EngineLaunch`; `EngineFactory.make` builds `AgentSession` (Claude, one long-lived process fed through stdin) or `CodexSession` (one `codex exec` process per turn behind the same stream). Every engine speaks the one conversation format the app renders: the engine adapters emit `ClaudeEvent`s (the name is historical; it is the shared event type) and the reducer never learns which engine produced them. The thread an engine assigns to itself travels as `ClaudeEvent.engineSession(engine:id:)`, is written to the transcript as a `session` line with that engine, and never replaces `ConversationState.sessionId`, which stays the conversation's identity. **Python bot** (`wisp_bot/engine.py`): `Engine` has `name`, `run(prompt, *, session_id, cwd, started, ...) -> Result` and `status() -> Status`; `Result` carries `engine` and `model` for the turn (written to the transcript). `session_id` is the id Wisp chose for Claude (`--session-id` / `--resume`) and the saved thread id for Codex, which assigns its own: `Result.session_id` is what to pass back next time. The bot has no in-turn approval channel of its own (its permission mode is fixed per turn); Claude turns pass `on_permission` (the `can_use_tool` card) and Codex turns pass the same callback to the email approval broker (`Engine.run(..., on_permission=...)`), so the bot answers email approvals for both engines with the same Permitir/Negar card. `respond` exists only on the Swift side, where `routesApprovals` says whether the engine routes the CLI's own tool approvals (Claude yes, Codex no); `CodexSession.respond` answers only the email broker's requests and throws `approvalsNotRouted` for any other id.
- Active engine: `ativo = "claude" | "codex"` at the top level of `<wisp_dir>/modelos.toml` (a key inside a `[table]` is ignored). One writer, `wisp config set engine <name>` (seeds the folder, writes the line and keeps the rest of the file, then syncs Claude and Codex rendering); readers are the app (`EngineChoice`) and the bot (`engine.active_name`); a missing, unreadable or unknown value means Claude. The file is per machine because the Wisp folder is local; nothing syncs it. Plan 4 adds more engine names and picks them in the full Modelo tab.
- Engine not usable on this machine: the app (`CodexReadiness`, `codex --version` and `codex login status`, exit 0 means logged in) and the bot (`engine.resolve`, status cached 30 s) run the turn on Claude and say so (a system line in the app, an italic note in Telegram). It is decided per turn, so installing or logging in takes effect on the next message.
- Switching engine in the middle of a conversation reuses the rebuild path of "Conversation transcript": the engine that answered the last reply (transcript `assistant` entries carry `engine`) is compared with the one about to answer; if they differ, or the new engine has no saved session, it starts a fresh session primed with the same memory block (last 6 messages, 24000 characters) and a one-line note names the engine ("↻ agora quem responde é o Codex; ele retomou pela conversa guardada no Wisp."). A Claude switch-back starts a new Claude session id (linked as `rebuilt`), exactly like a lost session. A Codex thread id is stored as a `session` line with `engine: codex` and resumed with `codex exec resume <id>` while Codex keeps answering; a resume that fails before any `turn.started` is treated as a lost session and rebuilt. A conversation that starts under Codex has **no `sessionId`** in the app (that field is only ever a Claude session id; nothing invents one): its identity is the conversation UUID, which is the transcript file name, and each engine only resumes its own id (`EngineResume.plan`: Codex never gets a Claude id, Claude never a Codex thread). The app reads history by that conversation id from Wisp's transcript whenever there is no Claude session or any reply came from another engine, because Claude's own session file only holds Claude's turns (`TranscriptHistory.load`). Sharing such a conversation to Telegram stays unavailable until a Claude turn gives it a session id.
- Resume rules (`EngineResume.plan`, core): each engine only ever resumes its own session id, so a Codex turn never sees the Claude id and a Claude turn never sees a Codex thread. A different engine than the one that answered last, a session that is gone, or one the engine never had means a fresh session primed from the transcript. A Claude conversation with no session id is now primed from the transcript instead of starting blank, and history falls back to the transcript.
- Safe folders: `safeDirectory` / `safe_dir` return the resolved path of a directory that is not home, a parent of home or `/`, else nothing; `workspace` is the conversation's folder when safe, else the Wisp folder when safe, else nil, and then the turn does not run on Codex. `TranscriptHistory.load` shows Wisp's transcript when any reply came from an engine other than Claude or when there is no Claude session (a Codex-only conversation, found by its conversation id), otherwise Claude's session file with the transcript as fallback. `engine.resolve` returns the engine for the turn and the note to show when the active one is unusable here. `sync_codex`'s merge reports added, updated, unchanged or conflict, and the digest to record. `EngineModel` (Ajustes > Motor) only reads `modelos.toml`; `wisp config set engine` writes it and renders Codex's files.
- What is left of the app-Telegram link: it still compares session ids. After a switch or rebuild on one side (a new Claude session id), the other surface keeps the old id until it rebuilds too; the transcript still finds both (`session` lines), but `TelegramTopics.topic(forSession:)`, the session lock and the follow/preview readers (Claude's session file) were not moved to conversation ids. Telegram follow mode and previews of a Codex-answered conversation show Wisp's transcript text only in the app's history; the bot's own topic note is unaffected.

## Local engine

- Unit: `cli/src/wisp/local/` (not wired into the app or the bot yet; plan 3 owns `ConversationRuntime.swift`, `claude_runner.py` and `ClaudeCommand.swift`). Run it on its own with `wisp local chat --message TEXT [--conversation ID] [--model TAG] [--mode default|auto|bypassPermissions] [--surface app|telegram] [--thread N]`; `wisp local catalog|pull TAG|install-ollama|use TAG` feed the picker. Every command prints one JSON object per line and exits 1 with `{"type":"error","message":...}`.
- Seam for plan 3 (`wisp.local.engine.LocalEngine`): `start(conversation, model, mode)` and `resume(conversation, model, mode)` return a `Session`; `await send(session, text, emit, model=None)` runs one turn and calls `emit(event)` for each event; `model` may differ on every turn and the tier, tools and context budget follow it. `resume` rebuilds the history from `conversas/<id>.jsonl` (only `user` and `assistant` text lines); the engine has no session store of its own, and it does not write the transcript: the caller records the user and assistant lines (`record_turn` does it for the CLI, with `engine: "local"` and the model). `send` is a coroutine with a callback, not an async generator, so cancelling it (a stopped conversation) unwinds the MCP servers and withdraws any pending approval in the same task.
- Events are Claude's stream-json lines, so `ClaudeStreamDecoder` renders them unchanged: `system/init` (`session_id` is the conversation id, `apiKeySource` "none", plus `engine`, `tier`), `assistant` with `text`, `thinking` and `tool_use` items (ids `toolu_local_*`), `user` with `tool_result` items, `result` (`result`, `is_error`, `permission_denials`, plus `engine`, `model`, `stopped` and `steps`). The golden stream is `cli/tests/fixtures/contract/local-engine-events.jsonl`; a Swift test decodes it. One assistant event per model reply (Ollama is read streaming, the reply is emitted whole). Notes the guardrails add to a reply ("↳ ...") are an `assistant` text event and are also appended to `result`.
- Approvals are the engine's own, in `wisp.local.approver`: `LocalEngine(approver=...)` takes an `Approver` (`async ask(tool, arguments, tool_use_id)` returning `allow`, `deny` or `timeout`; the default is `DenyApprover`, so an engine built without one runs no gated tool). The loop asks for: the irreversible tools (`email_send` and `run_shell` are the built-in floor), the tier's `approve` list, and in `default` mode every tool that is not read-only (`READ_ONLY` in `guardrails.py`; an unknown MCP tool counts as a write). `email_send` has no exemption: the email tool no longer asks by itself (Claude gates it with its `ask` rule; here the loop does), so it is carded in every mode and tier, and the call only reaches the tool after `allow`. Nothing the model can write or call answers a card: there is no approvals folder or decision file. `TtyApprover` (`wisp local chat`, default `--approvals tty`) prints the tool and its JSON arguments and reads the answer from `/dev/tty`, never stdin, so piped input cannot answer; only `s`, `sim`, `y` or `yes` allows, anything else, EOF or no terminal denies, and 600 s without an answer is `timeout` (denied). `StdioApprover` (`--approvals stdio`, the host spawns the process) writes Claude's `control_request` line on the event stream (`{"type":"control_request","request_id":"req_<hex>","request":{"subtype":"can_use_tool","tool_name","display_name","input","description","permission_suggestions":[],"tool_use_id"}}`, so `PermissionRequest` and the bot's `pedir_permissao` render it unchanged) and waits for the matching `control_response` on stdin (`response.subtype` `success` with `response.behavior` `allow` allows; `deny`, an error subtype, a closed stdin or 600 s without an answer deny; lines for other request ids and non-JSON lines are ignored). With `stdio` the message must come in `--message TEXT` (`-` is refused), because stdin belongs to the host's answers. A denied or timed-out call is named in `permission_denials` and the model reads "o usuário negou a ação" or "ninguém aprovou a tempo". `permission_suggestions` is empty, so "Sempre permitir" never shows for local tools. Not verified: the app and the bot do not spawn the local engine yet, so the stdio shapes are pinned by tests against a scripted host and the Swift/bot decoders' tests, not by a real app or bot run, and the TTY path was tested with a pipe standing in for `/dev/tty`, not a real terminal. `WISP_TELEGRAM_THREAD` is passed to the tool servers from `--thread`.
- Guardrails (`guardrails.toml`, validated on load; an invalid file stops the turn with the file, section and value, and nothing runs): tiers `pequeno`, `medio`, `grande` with `max_steps` (model replies per turn, 0 = no cap; the tools of the last allowed reply still run, then the turn stops), `tools` (allowlist) and `approve`; `[irreversible] tools` can only add to the built-in floor `email_send` and `run_shell` (code, not config); `[loop] repeat_limit`: the Nth identical call (same tool, same arguments) in a turn is not run and stops the turn. A call outside the allowlist is answered to the model as an error and named in the reply with a bigger-model suggestion. - `scripts/build-release.sh` picks the identity in this order: `WISP_SIGN_ID` (e.g. a Developer ID; `-` forces ad-hoc), then `Wisp Self-Signed` when `security find-identity -v -p codesigning` lists it, then ad-hoc. Any non-ad-hoc identity signs with `--timestamp` (Apple's timestamp server also stamps the self-signed certificate; checked on 2026-11-18). Only a `WISP_SIGN_ID` other than `Wisp Self-Signed` adds the hardened runtime and `scripts/wisp.entitlements` (Apple Events) on the app: under the hardened runtime, library validation refuses to load `Sparkle.framework` when the identity has no Team ID, and the app dies at launch with "mapping process and mapped file (non-platform) have different Team IDs" (seen on 2026-11-18). `WISP_NOTARY_PROFILE` notarizes and staples and needs `WISP_SIGN_ID` set, since Apple notarizes only Developer ID signatures. Sparkle's helpers (`Installer.xpc`, `Downloader.xpc` with its entitlements kept, `Autoupdate`, `Updater.app`, then the framework) are re-signed inside out with the same identity before the app.
- Stable signature: an ad-hoc build's designated requirement is its cdhash, so every build looks like a new app to the Keychain ("Always Allow" on the "Wisp — Spotify" item) and to macOS privacy grants. Signed with `Wisp Self-Signed`, the requirement is `identifier "ai.wisp.app" and certificate leaf = H"<sha1>"`, the same on every build and update. The identity (RSA 2048 self-signed certificate, code signing only, valid until 2036-11-15, trusted for code signing in the login keychain) lives only in the maintainer's login keychain and is never committed. Export a backup (Keychain Access > My Certificates > "Wisp Self-Signed" > Export, `.p12` with a password) and keep it off the repo. Losing it means a new certificate, so after the next update every user sees the Keychain and permission prompts once more. It does not replace a Developer ID: Gatekeeper still treats the download as unidentified.
- Local signing: the target's Debug and Release configurations take `app/Signing.xcconfig`, which signs ad-hoc (`CODE_SIGN_IDENTITY = -`) and then includes the optional, git-ignored `app/Local.xcconfig`. ## Updates (Sparkle)

- Sparkle 2.10.1 (exact pin). The feed is `SUFeedURL` = `releases/latest/download/appcast.xml` of the public repo, so only the release GitHub marks as latest is seen. Checks run daily (`SUScheduledCheckInterval` 86400) without asking first (`SUEnableAutomaticChecks`); downloads never install on their own (`SUAutomaticallyUpdate` and `SUAllowsAutomaticUpdates` NO), the user confirms in Sparkle's window.
- EdDSA signing key: the private key lives only in the maintainer's login Keychain (generic password, account `ed25519`, created by Sparkle's `generate_keys`); `generate_appcast` reads it from there. The public key is `SUPublicEDKey` in `app/project.yml`. Never export or commit the private key. Losing it means no installed copy accepts a new update: every user has to download and reinstall the DMG by hand (that build would carry a new public key).
- Versions: `CFBundleShortVersionString` comes from `MARKETING_VERSION` and `CFBundleVersion` from `CURRENT_PROJECT_VERSION` in `app/project.yml`; Sparkle compares `CFBundleVersion`, so it must grow on every release. v0.1.0 shipped with neither key in its Info.plist and no updater; 0.2.0 is build 2, 0.2.1 build 3.
- Gentle reminders: a scheduled check that finds a version posts the notch notice "Versão nova do Wisp — x.y.z" (kind `update`, own switch, on by default) instead of opening a window; the click calls `checkForUpdates`, which brings Sparkle's pending update window forward after `NSApp.activate()` (Wisp is `LSUIElement`). While only the setup window is up there is no notch, so Sparkle shows its own alert. With the switch off or "Não perturbe" nothing appears; Ajustes > Atualizações then shows the found version and "Ver atualização".
- Quarantine: Sparkle's installer releases the whole new bundle from quarantine (`releaseItemFromQuarantineAtRootURL`) before swapping it in, so an update never hits Gatekeeper. `RuntimeInstaller` still copies `uv` out of the bundle and strips the flag on its copy; on an updated app the flag is already absent and `removexattr` returns `ENOATTR`, which is accepted. A changed runtime `VERSION` reinstalls on the first launch after the update, as on a fresh install.
- Signature changes: Sparkle accepts an update whose EdDSA key matches the installed one even when the code signature changes (each ad-hoc build has a new one; 0.2.0 was ad-hoc, 0.2.1 is the first with `Wisp Self-Signed`).
- Debug only: `-WispUpdateFeed <url>` overrides the feed (via `feedURLString(for:)`) to test the flow against a local appcast. With a test feed the updater also runs a background check at start, so the reminder path needs no day's wait.
- Scheduled reminders go through `UpdateModel.notices`; it is nil while only the setup window is up, which makes Sparkle show its own alert. `available` holds the version found and not yet looked at, cleared on attention or when the session ends.
- `scripts/build-release.sh`: the appcast is signed with the Keychain key; its archives dir (`build/appcast`) holds only the DMG and its release notes page, so the zip in `dist/` never becomes a second entry of one version.
- `scripts/publish-release.sh <version> [notes-file]` publishes `dist/` as release `v<version>`; the feed reads `releases/latest/download/appcast.xml`, so the new release must be the latest. Notes default to the "Unreleased" part of the changelog.
- Guard limits: the harvest guard also denies any path with a `.git` or `.obsidian` component under the brain (every tool, Read included) and Glob patterns naming those segments; an absolute pattern with no static prefix (`/*/passwd`, `/{etc}/passwd`) resolves its prefix to `/` and is denied.
- Glob symlink limit: a wildcard segment that matches a symlink inside the brain is not followed by the check; the harvest model has no tool that creates symlinks.
- Stopping the harvest: stopping the scheduler (or quitting the app) cancels the running harvest, which sends SIGTERM to its process group and SIGKILL after 1 s, instead of waiting out the 1800 s timeout.

## core / Meetings

- Capture path: a source callback only copies samples into its `CaptureRing` (a preallocated single-producer single-consumer ring of 48 slots of 4096 frames, up to 4 channels, atomics only, no lock and no allocation; a full ring drops the chunk and counts an overrun). A 50 ms timer on one serial writer queue pops the rings, downmixes to mono, resamples to 48 kHz, mixes and writes. `MeetingRecorder` state is touched only on that queue.
- `StereoMixer`: L = mic, R = system, aligned by host time (`AudioTimeStamp.mHostTime` from the tap, `AVAudioTime.hostTime` from the engine, both converted by `HostClock`), not by arrival order. The origin is the earliest first chunk of the two sources: nothing is placed until both have delivered, or until one has more than `maxSkewFrames` (0.5 s) waiting, or on flush. A chunk that starts within `toleranceFrames` (25 ms) of where the lane ends is appended as contiguous, so timestamp jitter inserts nothing; further ahead it is preceded by silence, further behind its overlap is dropped, and anything before the already written position is dropped. Residual drift (the two clocks differ by some ppm) therefore builds up unnoticed up to 25 ms and is then corrected in one step by the gap or overlap rule; the tap's drift compensation is on as well. Past `maxSkewFrames` of difference the lagging lane is padded with silence so a source that goes quiet never stalls the file.
- `LinearResampler`: stateful across chunks (the result is the same however the input is cut); the same rate is a pass-through; a lane restarts its resampler when the rate of a slot changes (a device switch).
- File: during the call the audio goes to `audio.caf` (PCM 16-bit stereo 48 kHz), which a crash leaves readable; at stop it is encoded to `audio.m4a` and the CAF is deleted. If encoding fails the CAF stays, the status is `failed` and the result points at it. `RecordingRecovery.recover(root:)` runs at app launch: a folder whose `meta.json` says `recording` is encoded, the raw file removed and the status set to `interrompida` (audio ready but cut short; the ASR step must treat it like `transcribing`); an empty or unconvertible one becomes `failed` with the reason and keeps the raw file.
- `MeetingRecorder`: the folder name is the start time in the local zone, a second recording in the same second gets `-2`. Start order: support gate, folder, free-disk check, sink, mic, system; any failure removes the folder and stops what had started. Sources are stopped before the final flush and the rings are drained after that. Duration is frames written / 48000. `meta.json` ends as `transcribing` (nothing consumes it until the ASR step) or `failed`.
- Warnings (`warnings()`, shown in the pill as an amber dot and in the sidebar): a source that delivered no frames for 5 s ("o microfone parou" / "o áudio do Mac parou"; a source that never delivers is flagged 5 s after the start), an all-zero system channel for 10 s ("não estou ouvindo o áudio do Mac: libere em Ajustes do Sistema › Privacidade › Gravação de áudio"; shown once per recording, cleared when sound arrives; a Mac that is simply playing nothing for 10 s triggers it too), and ring overruns. `health()` is the fatal one: a write error or less than 200 MB free stops the recording.
- `CallAppCatalog.app(forBundleID:)`: exact id first, else the longest catalog id that is a dotted prefix (so `com.google.Chrome.helper` is Chrome). Browsers are `kind: .browser` since the id alone does not say it is a call.
- `MeetingCaptureSupport`: Core Audio process taps exist from macOS 14.2; below that the recorder refuses with a pt-BR message (the app's deployment target is 15, so it is a guard, not a path users hit).
- `recordingsPath` is read from the settings file only; its screen in Ajustes belongs to the Paths PR, which owns Ajustes > Caminhos.

## app / Meetings

- Start and stop run off the main actor (the model shows "Iniciando…" and "Salvando…" meanwhile and disables the row); quitting the app stops synchronously.
- `ProcessTapSource`: a global stereo tap (nothing excluded, not muted) read through a private aggregate device whose main sub-device is the default output at that moment. A listener on the default output device tears the tap and aggregate down and builds them again, leaving a short gap that the host-time alignment keeps in place. A denied system-audio permission is not an error from Core Audio; the right channel is just silent, which the 10 s warning reports. Not verified on real hardware yet.
- `MicrophoneSource`: refuses up front when the microphone permission is denied; "not determined" lets the engine start trigger the system prompt, only on the user's click. `AVAudioEngineConfigurationChange` removes the tap, reinstalls it with the new input format and restarts the engine; the rate and channel count travel with every slot, so nothing else needs rebuilding.
